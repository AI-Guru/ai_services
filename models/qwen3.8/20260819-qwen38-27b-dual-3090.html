Qwen3.8-27B · vLLM · 2026-08-19

256K on Two 3090s

Serving Qwen3.8-27B at its full 262,144-token context on a pair of RTX 3090s — what fits, what it costs, why the second card is not optional, and where speculative decoding pays for itself.

2 × RTX 3090 24 GB SM 8.6 Ampere NVLink NV4 · 56 GB/s driver 590.48.01 vLLM 0.16.1rc1 image cu130-nightly

Result

Q4 on two cards is the configuration

Three configurations were built and measured end to end. Single-stream decode from test_chat.py --runs 3 --warmup; context claims verified by needle-in-haystack retrieval, not by what the startup log promised.

Q4 + MTP-2 · 2 GPU 74.6tok/s Full context and the fastest result. Speculation is nearly free here. 256K verified
FP8 · 2 GPU 47.3tok/s First-party checkpoint, full context, but 37% slower. 256K verified
Q4 + MTP-2 · 1 GPU 55.4tok/s Best single-card speed, but context collapses to 48K to pay for it. 48K ceiling

Why

Q4 wins decode, and does nothing for prefill

The 48% decode gain over FP8 is not a quantization-quality trade dressed up as speed — it is bandwidth. Decode on a dense 27B drags the entire weight set across the memory bus once per generated token, so time-per-token tracks bytes-of-weights. 19 GB instead of 29 GB is the whole story.

Prefill is compute-bound instead, and there the two are indistinguishable: 965 vs 954 tok/s on the same 252,058-token prompt. That gap is noise. If your workload is long-prompt / short-answer, Q4 buys you almost nothing.

Speculation

MTP pays most where the target is slowest

Qwen3.8-27B ships an MTP head (mtp_num_hidden_layers=1), and both checkpoints carry its weights — including the community Q4, which leaves the draft head unquantized in BF16 while the target is 4-bit. Draft length was swept at 1, 2 and 3.

Two is the only setting that works. One draft token does not earn back its extra forward pass. Three loads happily, reports a healthy 12.07 GiB KV pool, and then dies on the first request with a 256 MiB Triton-autotune OOM — vLLM's startup sizing does not account for the longer draft's workspace.

The single card gains three and a half times as much, and the mechanism explains why. MTP amortizes one pass over the weights across several verified tokens. TP1 carries all ~19 GB of weights on one card; TP2 splits them. The more bandwidth-starved the target, the more each avoided weight-load is worth — so the payoff scales inversely with how fast the target already is.

That is the same relationship the README hit on the RTX PRO 6000, read from the other end: there, MTP got worse as the NVFP4 target got faster. Nothing contradicts; speculation is simply priced against the target it is speculating for.

On one card, MTP is a trade, not a win

The draft head costs 0.86 GiB on a card that had none to spare. KV falls 3.23 → 2.37 GiB and the pool from 25,088 → 17,600 tokens, so the verified context ceiling halves: 96K without MTP, 48K with it. Single-card users are choosing between 44.9 tok/s at 96K and 55.4 tok/s at 48K — there is no setting that gives both.

On two cards no such trade exists. KV only moves 12.66 → 12.07 GiB and the full 262,144 survives intact, which is why MTP-2 is the recommended configuration rather than an optional extra.

The budget

Sharding halves the weights — that is what buys 256K

The instinct is that two cards give 48 GB and 256K needs more than 24. That is the wrong model. Tensor parallelism splits the weights across both GPUs, and the space freed on each card is where the KV cache goes. Going from one card to two does not just add capacity; it removes 8.3 GiB of weights from the card that has to hold the cache.

Only 16 of 64 layers hold a growing cache

Qwen3.8-27B is hybrid — full_attention_interval=4 means 48 Gated DeltaNet layers and 16 full-attention layers. DeltaNet keeps a fixed-size recurrent state; only the 16 attention layers grow with sequence length. That is the only reason 256K is reachable on 48 GB at all:

KV per token = 16 layers × 4 KV heads × 256 head_dim × 2 (K+V)
             = 32,768 elements/token

  fp16 KV   64 KiB/token   →  262,144 tokens = 16 GiB
  fp8  KV   32 KiB/token   →  262,144 tokens =  8 GiB   ← used here

A 64-layer all-attention model of the same shape would need four times this, and none of the configurations below would exist.

Traps

Ten things that cost time

vLLM's custom all-reduce is broken on 2×3090

Without --disable-custom-all-reduce the server dies during warm-up with Cuda error custom_all_reduce.cuh:455 'invalid argument'. P2P is fine (can_device_access_peer true both ways, no IOMMU on the cmdline) — the kernel simply does not work here. NCCL fallback is correct and costs nothing measurable.

The traceback points at _initialize_kv_caches → compile_or_warm_up_model, which reads like an OOM or a KV sizing bug. It is neither. Read the CUDA error line above the traceback.

The one-card OOM happens in Triton, not in the KV cache

At the moment TP1 died on a 110K prompt, KV usage was 4.6% and the scheduler was on the first 2048-token chunk. The allocation that failed was Triton's autotuner asking for a 256 MiB benchmark buffer (do_bench → get_empty_cache_for_benchmark). Judging headroom by the KV-usage number would tell you there was plenty of room.

It takes the whole server with it — every in-flight request 500s. With restart: unless-stopped that becomes a crash-loop.

The reported KV pool size is a 4× underestimate

vLLM logs GPU KV cache size: 114,464 tokens for FP8/TP2 and Maximum concurrency for 262,144 tokens: 1.72x — yet that config served a 252,058-token request without trouble. The counter prices every one of the 64 layers as if it held a growing cache; only 16 do. Trust a probe, not the log line.

--max-num-seqs defaults to 1024 and that is catastrophic here

The DeltaNet recurrent state is ~37 MB per sequence slot per GPU across the 48 linear-attention layers. At the default, the state pool alone would want tens of GB and leave nothing for KV. All three configs pin it to 32.

FP8 on Ampere is a memory format, not math

SM 8.6 has no FP8 tensor cores. vLLM logs it plainly — “Your GPU does not have native support for FP8 computation… Weight-only FP8 compression will be used leveraging the Marlin kernel.” You get the 29 GB footprint that makes the model fit, at Ampere BF16 math rates. Nothing about the FP8 numbers here transfers to a card that has the tensor cores.

Everything fast in the existing README is Blackwell-only

The production config in README.md — NVFP4 W4A4 + DSpark + probabilistic drafting, 108–122 tok/s — needs SM 100/120 FP4 tensor cores. None of it runs on this host, and none of its numbers are comparable to anything measured here. Those results were taken on the RTX PRO 6000.

--no-think is a no-op on this family

Confirmed again: test_chat.py --no-think still produced 1,444–25,651 characters of reasoning. The script's “TTFT” is therefore time-to-first-answer-token — it includes the entire thinking phase, which is why it reads 4.2 s to 126 s. True first-token latency was measured separately and is 76–98 ms warm. Use reasoning_effort: low, not enable_thinking:false.

MTP on one card does not fail — it hangs

A 64K request to the TP1+MTP config began prefilling, reached 45.5% KV usage, and then the engine loop went silent: no further log output, GPU pinned at 100% / 330 W / 79 °C, for 48 minutes. No timeout, no exception, no crash. /health returned 200 OK the entire time, so health-based supervision believes the server is fine and the client waits forever.

This is strictly worse than the clean OOM the non-MTP TP1 config gives you. Recovery is docker compose down (~10 s; GPU released cleanly, no Xid, no crash dump). If you tune --max-model-len upward here, watch the engine's periodic “Avg generation throughput / Running: N reqs” lines and treat their disappearance — not an error — as the failure signal.

MTP-3 passes startup and dies on the first request

Draft length 3 loads, reports 12.07 GiB of KV and 2.69× concurrency at 262,144, and reads as perfectly healthy. The first request kills it with the same 256 MiB Triton-autotune OOM. Startup memory sizing does not model the longer draft's workspace, so “it started” proves nothing.

draft_sample_method: probabilistic does not exist in stock vLLM

The README's +10% from probabilistic drafting cannot be reproduced on vllm/vllm-openai:cu130-nightly. SpeculativeConfig rejects the key outright — pydantic ValidationError: unexpected_keyword_argument. It must be a patch carried by the Blackwell-specific qwen38-x86_64-cu130 image. Budget nothing for it here.

Quality

fp8 KV checked, not assumed

256K only fits with --kv-cache-dtype fp8, and vLLM warns that the checkpoint ships no q/prob scaling factors. On this model family fp8 KV has a history of silent corruption (vllm-project/vllm#26646 on Qwen3.6), so the failure mode is wrong answers rather than a crash. Every configuration was spot-checked before its numbers were recorded — arithmetic (17×23+145 → 536), factual recall, code retention, and needle retrieval at full length. All passed on all three.

That is a smoke test, not an evaluation. It rules out gross corruption; it does not establish that long-context reasoning quality is unharmed. On Q4/TP2 there is enough headroom to drop --kv-cache-dtype entirely and run a fp16 cache at 256K — the option does not exist on the FP8 config.

Reproduce

Files and commands

Five new compose files; nothing existing was modified. They are named for this hardware (-3090) to keep them distinct from the RTX PRO 6000 configs alongside them.

# 2 GPUs, Q4 + MTP-2, full 256K — the recommended configuration
docker compose -f docker-compose.vllm-27b-q4-mtp-tp2-3090.yml up -d  # :11488

# 2 GPUs, Q4, full 256K — no speculation
docker compose -f docker-compose.vllm-27b-q4-tp2-3090.yml up -d      # :11486

# 2 GPUs, first-party FP8, full 256K
docker compose -f docker-compose.vllm-27b-fp8-tp2-3090.yml up -d     # :11485

# 1 GPU, Q4, 96K ceiling
docker compose -f docker-compose.vllm-27b-q4-tp1-3090.yml up -d      # :11487

# 1 GPU, Q4 + MTP-2 — faster, but only 48K
docker compose -f docker-compose.vllm-27b-q4-mtp-tp1-3090.yml up -d  # :11489

# benchmark
python3 ../shared/test_chat.py --base-url http://localhost:11488/v1 \
    --model qwen3.8-27b --runs 3 --warmup --no-think

Checkpoints: Qwen/Qwen3.8-27B-FP8 is first-party. The Q4 configs use philbert440/Qwen3.8-27B-W4A16-AWQ — a community quant (Qwen ships no official INT4 for 3.8-27B), compressed-tensors pack-quantized, 4-bit, group size 128, vision tower left in BF16. Unvetted beyond the smoke tests above.
