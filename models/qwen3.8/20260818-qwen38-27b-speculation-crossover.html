The finding

Two configs, opposite answers

Every published benchmark for this model measures one request at a time. That number ranks configurations in an order that reverses almost exactly once the card is actually busy.

Aggregate throughput vs concurrency — chat workload2,000 in / 300 out · GuideLLM

Four speculative-decoding strategies on the identical W4A4 NVFP4 checkpoint. The only thing that changes is how many tokens the drafter proposes per step.

At one request in flight, DSpark-7 + probabilistic leads by 58% over no speculation at all. By concurrency 30 it is dead last — behind even the config that does no speculative decoding whatsoever. Meanwhile MTP-2 + probabilistic, which gives up 3% single-stream, delivers 30% more aggregate throughput at the load a real endpoint actually sees.

The mechanism

Speculation is free until the GPU is busy

The crossover is not an artifact. It follows directly from what the card is bottlenecked on, and the bottleneck changes as the batch fills.

Decoding one token requires reading all 17.5 GB of weights. At 1.79 TB/s that is 9.8 ms, and it is the same 9.8 ms whether you verify one draft token or sixteen — the arithmetic to check them is rounding error next to the memory traffic:

Cost of one verify step vs draft block sizeweights 17.5 GB · 1.79 TB/s · ~1.5 PFLOPS FP4

Weight-read time is flat; compute is negligible at every block size that fits. This is why a long draft block is nearly free for a single user — and why it stops being free when many users share the step.

Once enough requests share a step, the GPU flips from memory-bound to compute-bound. Now every drafted-but-rejected token is real work stolen from a real request. Draft cost per request per step becomes the thing that decides throughput — and it orders the table perfectly, in both directions:

Draft length is the whole storysame checkpoint · same engine

At concurrency 1, throughput rises monotonically with draft length. At concurrency 30 the curve inverts into a peak at two tokens. Nothing else about these configurations differs.

The rule this gives you

The optimal draft length falls as concurrency rises. A single-stream draft-length sweep — the thing every checkpoint card publishes — is therefore the wrong instrument for choosing a production configuration. It is measuring the memory-bound regime and your endpoint runs in the compute-bound one.

The single largest lever, and it is invisible from the repository name. On sm_120 the FP4 tensor cores only engage when the activations are 4-bit too; a W4A16 checkpoint dequantizes and runs the GEMM at 16-bit, buying VRAM and nothing else.

Mixed load

Under DSpark, images pay double

A multimodal endpoint gets text-only and image-bearing requests in the same batch. That combination is where the two speculative strategies separate hardest — and it is not visible in any text-only benchmark.

vLLM says the quiet part out loud at startup and then carries on serving:

Draft model Qwen3DSparkForCausalLM does not support external multimodal embeddings. Embeddings from the target model will not be passed to the drafter; using text-only draft inputs instead.

So on every image turn the DSpark drafter is guessing from text alone, and the draft compute is wasted. MTP is part of the target model and reads its hidden states, so it has no such blind spot.

Per-stream throughput on a 50/50 text+image batchconcurrency 32 · 128 requests · 0.5–4.75 MP images

Text and image requests interleaved in the same batch. A balanced pair of bars means the strategy treats both modalities alike; a short right-hand bar means image requests are subsidising the drafter.

The gap is a factor of 1.7

Under DSpark-7 an image request decodes at 18.4 tok/s while a text request in the same batch gets 31.8. Under MTP-2 + probabilistic the two are 36.1 and 38.1 — within a few percent of each other. For a vision endpoint this settles the choice on its own, before throughput is even considered.

Capacity

Speculation is rented from the KV cache

Draft slots are not free in memory either. They come out of the same pool that determines how many long-context users fit on the card at once.

KV cache pool by configuration--gpu-memory-utilization 0.88 · 262 K max context

The right-hand figure is how many simultaneous requests at the full 262,144-token context the pool supports. DSpark-7 gives up nearly half the pool relative to no speculation.

What the drafter is guessing about

Two more results that decide how much any of this transfers to your traffic.

One retraction

A DSpark-3 run first appeared to crash under load — GuideLLM reported a dead worker group, then every request got connection-refused. A clean re-run passed with the engine still running and zero error lines in its log. It was the benchmark harness that died, not the server. From the client side those two look identical, so the test rig now always saves the engine log.

Verified on the deployed configuration

Speed that breaks correctness is not speed. The production config was re-checked after deployment, with speculation active throughout:

  • Tool calling 4/4, including three parallel calls folded into one answer.
  • Vision at 0.5, 1.05 and 4.75 MP — the last is 4,663 prompt tokens, well past the 2,048-token tokenizer trap that breaks community repacks.
  • Needle-in-haystack recall exact at 43,247 tokens, needle at 85% depth.
  • Byte-identical output across three runs at temperature 0 — rejection sampling is lossless, and a correct drafter cannot change the output distribution. It doesn't.
  • Zero failed requests across five concurrency scenarios to 64 and mixed-modality bursts to 32.

Method, and how to disagree with it

Two throughput protocols are reported throughout because for speculative configurations they genuinely disagree. Sampled uses the model's own generation_config (temperature 1.0, top_p 0.95, top_k 20) with thinking on — how the endpoint is really used. Greedy uses temperature 0 with thinking off and ignore_eos — the protocol every vendor checkpoint card quotes. Speculative acceptance is a function of the target's sampling distribution, so quoting one against the other compares two different experiments.

The control that makes the rest trustworthy: with speculation off, all three protocols agree to within 2% (77.1 / 77.3 / 78.8 tok/s). Every disagreement elsewhere is acceptance-rate sensitivity, not benchmark noise.

Two measurement traps worth inheriting. GuideLLM's TTFT is unusable against vLLM — its median reads ~0 ms because vLLM emits an SSE frame with an empty role delta the instant a request is admitted, and the harness timestamps that as the first token; judge responsiveness by request latency instead. And counting stream chunks undercounts throughput roughly twofold, but only when speculation is working — vLLM packs every token accepted in one verify step into a single SSE frame, so the fastest configs look the slowest. Read usage.completion_tokens. That bug produced a 51.5 tok/s reading for a configuration actually running at 112.3 before it was caught.

Cross-boot spread on this card is about 3%; differences smaller than that are not read as real. Concurrency figures are GuideLLM's achieved mean, so a requested 32 reports as ~30.
