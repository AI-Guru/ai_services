A **dense transformer** processes every token through the full set of weights in each layer.  
A **mixture-of-experts (MoE) model** replaces one or more dense layers—usually the feed-forward network—with many “expert” sub-networks, and a small router selects only a few experts per token.

The core efficiency trade-off is:

> **MoE models can have far more total parameters than a dense model while keeping the number of parameters activated per token much lower.**

That gives better scaling and compute efficiency, but adds memory, communication, routing, and training-stability costs.

---

## 1. Architectural difference

### Dense transformer

For each token, every layer computes the full attention and feed-forward transformations:

\[
\text{token} \rightarrow \text{attention} \rightarrow \text{FFN} \rightarrow \text{output}
\]

All parameters in that layer are used for every token.

Consequences:

- Regular, predictable compute graph.
- Every token sees the same parameters.
- Compute cost scales directly with total parameter count.
- Easier to train and deploy with standard dense-model infrastructure.

### Mixture-of-experts transformer

Each MoE layer has multiple expert networks, for example:

\[
\text{token} \rightarrow \text{router} \rightarrow \text{top-k experts} \rightarrow \text{output}
\]

The router assigns a weight to each expert and typically selects only a small number, e.g. top-2 out of 8 or 16 experts.

Consequences:

- Different tokens use different experts.
- Only a subset of parameters is active per token.
- Total model capacity can be increased without proportionally increasing per-token compute.
- Adds routing overhead and load-balancing challenges.

---

## 2. Active parameters vs. total parameters

This is the central difference.

### Dense model

If a layer has \(P\) parameters, then every token activates \(P\) parameters.

Total parameters \(\approx\) active parameters.

So increasing model size usually means increasing per-token FLOPs.

### MoE model

Suppose a layer has 8 experts, each with the same size as the original dense FFN, and the router uses top-2 selection.

Total expert parameters:

\[
8 \times P_{\text{expert}}
\]

Active parameters per token:

\[
2 \times P_{\text{expert}}
\]

So compared with a dense FFN of size \(P_{\text{expert}}\), the MoE model has:

- 8× the expert parameter capacity.
- 2× the active expert compute per token.
- A much larger total model for the same active compute.

That is the main efficiency advantage: **MoE decouples model capacity from per-token compute cost.**

---

## 3. Compute efficiency

### Dense model

- High FLOPs per token.
- Computation is regular and usually well suited to GPUs/TPUs because dense matrix multiplication is highly optimized.
- If you want a larger model, you directly pay more compute.

### MoE model

- Lower FLOPs per token relative to a dense model with the same total parameters.
- Can scale model capacity more cheaply.
- Often achieves better loss or capability at a given compute budget.
- But the active experts are smaller, so individual expert computations may have lower arithmetic intensity than a single large dense layer.

In practice, MoE models are especially effective when the goal is to scale total model size while keeping inference or training compute per token manageable.

---

## 4. Memory and storage trade-offs

### Dense model

Memory cost is proportional to active parameter count.

For a given model size, all parameters are used, so memory utilization is straightforward.

### MoE model

MoE models store all experts, even though only a few are active for a given token.

Therefore:

- Total model memory is larger.
- Optimizer state memory during training can be much larger if all experts are trained.
- Inference may require storing many more parameters than are used per token.

This is one of the main costs of MoE: you gain compute efficiency, but often pay in memory footprint.

For inference, this matters a lot. A MoE model may be faster in FLOPs than a dense model, but if all experts do not fit in fast on-device memory, it may be slower in wall-clock time.

---

## 5. Communication and parallelism trade-offs

### Dense model

Dense models are usually easy to parallelize with standard techniques such as tensor parallelism, pipeline parallelism, or data parallelism.

Communication patterns are regular and well understood.

### MoE model

Because different tokens may be routed to experts on different devices, MoE often uses **expert parallelism**.

This introduces communication costs:

- Tokens must be routed to the correct expert.
- Tokens may need to be sent to a different device.
- Results must be sent back.
- The system may need all-to-all communication.

So MoE adds communication overhead that dense models do not have.

On a single device, routing overhead may be small.  
Across many devices, communication can become a major bottleneck.

---

## 6. Load balancing and utilization

In a dense model, every token uses every layer, so utilization is uniform.

In MoE, token routing can be uneven:

- Some experts receive many tokens.
- Some receive few.
- Some experts may become “hot spots.”
- Capacity limits can force token dropping or queuing.

To avoid this, MoE models usually use load-balancing losses or other techniques to encourage even expert usage.

This creates another trade-off:

- Better load balancing improves throughput and stability.
- But it can slightly hurt modeling quality or add training complexity.

MoE efficiency also depends on batch size. With large batches, expert utilization tends to be smoother. With very small batches, a few tokens may all route to the same experts, making computation less predictable and potentially less efficient.

---

## 7. Training stability

Dense transformers are generally easier to train.

MoE models introduce additional challenges:

- Router collapse: the model may stop using most experts.
- Expert starvation: some experts are rarely used.
- Load imbalance: some devices become bottlenecks.
- Capacity overflow: too many tokens route to one expert.
- Training instability: routing decisions and expert specialization can make optimization harder.

As a result, MoE models often need careful design choices:

- Number of experts.
- Top-k selection.
- Expert size.
- Router architecture.
- Load-balancing loss.
- Expert capacity.
- Warm-up schedules.
- Token dropping policies.

So MoE can be more compute-efficient, but it is usually more complex to train reliably.

---

## 8. Inference efficiency

### Dense model inference

For a dense model:

- Every token does the same amount of work.
- Latency is relatively predictable.
- Throughput scales well with batch size.
- Compute is often the dominant cost.
- Memory bandwidth matters, but all weights are used.

### MoE inference

MoE inference can be:

- Faster in FLOPs than a dense model of the same total size.
- More efficient for large models because only a subset of experts is active.
- Better suited to scaling total parameters without exploding per-token cost.

But it may also be:

- Slower in wall-clock time if expert communication is expensive.
- Slower if all experts do not fit in memory.
- Less efficient at very small batch sizes.
- Sensitive to expert placement and routing overhead.

A rough way to think about it:

> Dense models are compute-bound.  
> MoE models are often memory- and communication-bound.

---

## 9. Quality and scaling trade-offs

MoE models can often outperform dense models at the same compute budget because they can have a much larger total parameter count.

For example, a MoE model might have:

- 500B total parameters.
- 50B active parameters per token.

A dense model with 50B active parameters would have far less capacity. A dense model with 500B parameters would have much higher per-token compute.

So MoE can sit in a favorable scaling region:

- Larger total capacity than a dense model with the same active compute.
- Lower per-token compute than a dense model with the same total capacity.

However, this advantage is not free. It depends on:

- Whether experts are used effectively.
- Whether routing is stable.
- Whether the hardware can handle expert parallelism.
- Whether the memory footprint is acceptable.
- Whether batch size is large enough for good load balancing.

## Summary table

| Dimension | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Parameters used per token | All parameters in each layer | Only selected experts |
| Total vs. active parameters | Roughly equal | Total can be much larger than active |
| Compute per token | Higher for large models | Lower for large total models |
| Memory footprint | Smaller for same active compute | Larger because all experts are stored |
| Communication cost | Lower | Higher due to expert routing |
| Training simplicity | Simpler | More complex and less stable |
| Load balancing | Uniform | Non-uniform without careful design |
| Hardware utilization | Highly regular dense matmul | More variable, batch-dependent |
| Scaling behavior | More parameters = more FLOPs | Can increase capacity without proportional FLOPs |
| Main advantage | Simplicity and efficient dense compute | Compute-efficient scaling of model capacity |
| Main drawback | Compute grows with model size | Memory, communication, and routing overhead |

---

## Bottom line

A dense transformer uses every parameter for every token, so increasing model size directly increases compute. A mixture-of-experts model keeps many experts in memory but activates only a few per token, allowing it to scale total model capacity more cheaply.

The trade-off is:

- **MoE gains:** better compute efficiency, larger capacity at fixed compute, improved scaling.
- **MoE costs:** more memory, more communication, harder training, load-balancing challenges, and potentially lower hardware efficiency in some settings.

MoE models are therefore most attractive when you want a very large model but cannot afford the compute cost of a dense model of equivalent size. Dense models remain simpler and often more efficient when parameter memory is not the bottleneck and standard dense inference/training infrastructure is well optimized.
