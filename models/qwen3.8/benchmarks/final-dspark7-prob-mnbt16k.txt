Mixture-of-experts (MoE) models and dense transformers differ mainly in **when and which parameters are used** to process each token.

## Dense transformer

A dense transformer applies the same set of parameters to every token.

For example, in a typical dense Transformer layer:

- every token goes through the attention block;
- every token goes through the feed-forward network;
- all parameters in those blocks are active for every token.

So if the model has 7B parameters, roughly 7B parameters participate in the computation for each token.

**Efficiency profile:**

- Compute cost scales directly with model size.
- Behavior is predictable: same token count, sequence length, and batch size give roughly the same FLOPs.
- Memory footprint is proportional to total model size.
- Easier to train, serve, profile, and optimize because the computation graph is fixed.

The key trade-off is simple:

> To get a larger, more capable dense model, you must increase per-token compute and memory bandwidth usage.

---

## Mixture-of-experts transformer

In an MoE model, at least some layers replace the single feed-forward network with multiple parallel “experts.”

A router or gating network looks at the current token and selects a small subset of experts, for example:

- choose top-1 expert out of 8, or
- choose top-2 experts out of 32.

Only the selected experts are computed for that token.

A MoE model therefore has two different parameter counts:

1. **Total parameters**  
   All experts exist and must be stored.

2. **Active parameters per token**  
   Only the routed experts are used for a given token.

For example, a model could have:

- 100B total parameters, but
- only 10B active parameters per token.

This is the central idea behind MoE:

> Store a much larger model than the per-token compute budget would normally allow.

---

# Key efficiency trade-offs

## 1. Capacity vs. per-token compute

Dense models increase capacity and compute together.

If you make a dense model larger:

- more parameters,
- more multiply-accumulate operations per token,
- more memory traffic,
- higher latency.

MoE models decouple these.

By adding more experts but routing each token to only a few, you can increase the total number of parameters without increasing active compute per token proportionally.

This lets MoE models store more “knowledge” or representational capacity while keeping the active FLOPs lower than a dense model of the same total size.

**Trade-off:**

- MoE can give higher quality for a given active compute budget.
- But it does not reduce compute compared to a dense model with the same number of active parameters.
- It trades higher memory/storage and routing overhead for greater capacity at the same active compute.

---

## 2. Total parameter memory vs. active compute

MoE models can have a large total parameter count even if the active parameter count is modest.

This creates a tension between:

- **storage/memory efficiency** and
- **compute efficiency**.

Example:

| Model type | Total params | Active params/token |
|---|---:|---:|
| Dense 7B | 7B | 7B |
| MoE 50B total / 10B active | 50B | 10B |
| Dense 50B | 50B | 50B |

Compared with a dense 50B model, the MoE model is much cheaper to run per token.

But compared with a dense 10B model, the MoE model still requires storing many more weights.

So MoE can be:

- compute-efficient relative to a dense model of the same total size;
- memory-expensive relative to a dense model of the same active size.

This is one of the most important efficiency trade-offs.

---

## 3. Inference latency vs. throughput

MoE models often perform best in high-throughput, batched serving scenarios.

At large batch sizes, many tokens are processed together. Different tokens may route to different experts, and the system can amortize the cost of loading expert weights across many tokens.

So MoE models can be very good for:

- large inference batches,
- asynchronous serving,
- datacenter workloads,
- throughput-oriented inference.

However, for small-batch or single-stream latency-sensitive workloads, MoE can be less favorable.

Why?

- routing adds overhead;
- token-dependent expert selection makes compute less uniform;
- expert weights may cause more cache misses;
- different experts may be needed for different tokens;
- memory bandwidth may still be a bottleneck even if FLOPs are low.

**Trade-off:**

- MoE can improve throughput.
- But it may increase tail latency and make small-batch inference less efficient.

---

## 4. Memory bandwidth limitations

Transformers are often memory-bandwidth-bound at inference, especially on GPUs.

MoE models may perform fewer FLOPs per token than a large dense model, but they may still need to move a large amount of expert weight data through memory.

If the hardware cannot quickly fetch the relevant experts, the theoretical compute savings may not translate into proportional speedup.

MoE models can therefore be:

- more energy-efficient in terms of arithmetic;
- but not necessarily faster if memory bandwidth is the limiting resource.

This is a major practical trade-off:

> Lower FLOPs do not automatically mean lower latency if the model still moves more weight data from memory.

---

## 5. Routing overhead

MoE models add a routing step.

For each token, the router must:

- score experts;
- select the top-k experts;
- route the token to the appropriate expert(s);
- often handle load balancing;
- combine expert outputs.

This introduces overhead that dense models do not have.

The overhead can come from:

- routing computation;
- token sorting or binning;
- dynamic dispatch;
- load balancing;
- communication in distributed settings;
- variable-length expert computation.

**Trade-off:**

- MoE can reduce active expert compute.
- But it introduces routing and scheduling overhead.
- The net efficiency depends on how cheaply the system can implement routing.

---

## 6. Load balancing and capacity factors

A practical MoE issue is that tokens do not distribute uniformly across experts.

Some experts may be chosen more often than others, causing:

- some experts to be overloaded;
- some experts to be underused;
- training instability;
- wasted capacity if overloaded experts must drop tokens;
- uneven memory usage across devices.

To mitigate this, MoE training often uses:

- auxiliary load-balancing losses;
- expert capacity factors;
- token dropping or overflow buffers;
- expert replication;
- auxiliary router regularization.

These mechanisms improve practical efficiency but add complexity.

**Trade-off:**

- MoE can scale capacity more flexibly.
- But it is harder to train stably and efficiently than dense models.
- Poor load balancing can waste expert capacity and degrade training quality.

---

## 7. Training efficiency vs. serving efficiency

MoE models can be attractive for training because they allow a larger model capacity without a proportional increase in per-token compute.

This can help when:

- you want a large model;
- training compute is limited;
- you want more capacity without increasing active FLOPs too much.

However, MoE training has additional costs:

- optimizer states for all experts, not just active ones;
- expert parallelism;
- all-to-all communication;
- routing overhead;
- load-balancing management;
- larger checkpoint sizes.

So MoE can be compute-efficient in terms of FLOPs, but not necessarily total-training-memory- or communication-efficient.

**Trade-off:**

- MoE can reduce active compute during training.
- But it may increase memory, communication, and implementation complexity.

---

## 8. Predictability and engineering simplicity

Dense models are much easier to reason about.

For a dense model:

- the computation graph is static;
- FLOPs are easy to estimate;
- latency is easier to predict;
- kernels can be optimized more uniformly;
- serving systems do not need dynamic expert routing.

MoE models introduce dynamic behavior:

- which experts are used depends on the token;
- load across experts changes;
- device placement of experts becomes important;
- batching behavior can become less predictable;
- performance depends heavily on hardware and parallelism strategy.

**Trade-off:**

- MoE offers more architectural flexibility and capacity scaling.
- Dense models offer better predictability and simpler engineering.

---

## 9. Quality per FLOP vs. quality per total parameter

MoE is often attractive because it can improve quality for a given active compute budget.

A MoE model with:

- 100B total parameters,
- 10B active parameters,

may outperform a dense 10B model because it has more total capacity.

But if you compare it to a dense 100B model, the MoE model is much cheaper to run, though it may still have lower quality than the full 100B dense model depending on how much capacity the dense model uses.

So the efficiency depends on what you are holding fixed:

- **Fixed active FLOPs:** MoE may be better.
- **Fixed total parameters:** dense may use more compute.
- **Fixed memory budget:** dense may be easier to deploy.
- **Fixed latency target:** dense smaller model may be preferable.

# Summary table

| Dimension | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Parameter usage | All parameters active for each token | Only a subset of experts active per token |
| Total model size vs. active compute | Coupled | Decoupled |
| Per-token FLOPs | Scales with total model size | Can stay low while total params grow |
| Memory footprint | Proportional to total params | Often larger than active compute suggests |
| Inference latency | More predictable | Can be higher due to routing and expert dispatch |
| Inference throughput | Good at small and large batches | Can excel in large-batch, high-throughput serving |
| Memory bandwidth | Predictable | May be bottlenecked by expert weight fetching |
| Training | Simpler, more stable | More complex; needs load balancing and expert parallelism |
| Communication overhead | Lower in many settings | Higher if experts are sharded across devices |
| Engineering complexity | Lower | Higher |
| Main efficiency benefit | Simplicity, predictability, low memory footprint | Larger capacity without proportional active compute |

---

# Core intuition

Dense transformers are like a standard pipeline:

> Every token uses the full model.

MoE models are like a dynamic routing system:

> Each token only uses the relevant experts.

The main efficiency trade-off is:

> MoE lets you build a larger model without increasing active compute per token, but at the cost of higher total memory, routing overhead, load-balancing complexity, communication costs, and less predictable inference behavior.

So MoE is most attractive when you want:

- large model capacity,
- limited active compute,
- high-throughput serving,
- and enough hardware memory and batching to absorb the larger weight footprint.

Dense models are most attractive when you want:

- lower latency,
- smaller memory footprint,
- simpler deployment,
- predictable performance,
- and efficient operation on latency-sensitive or resource-constrained devices.
