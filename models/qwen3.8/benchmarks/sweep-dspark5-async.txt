Mixture-of-experts (MoE) and dense transformers both use the same high-level Transformer stack—attention plus feed-forward blocks—but they differ fundamentally in how computation is allocated across tokens.

### 1. Basic architectural difference

**Dense Transformer**
- Every token passes through every parameter in the model.
- Total parameters ≈ active parameters.
- For a 7B dense model, roughly 7B parameters are computed per token.

**Mixture-of-Experts Transformer**
- Usually the feed-forward layers are replaced by many smaller “expert” FFNs.
- A lightweight router predicts which experts to use for each token.
- Typically only top-1 or top-2 experts are activated per token.
- Total parameters can be large, but active parameters per token are much smaller.

Example:
- Dense 10B model: 10B active parameters.
- MoE model with 40B total parameters and top-2 routing: maybe 10B active parameters, but 40B stored in memory.

The key distinction is that MoE decouples **total capacity** from **per-token compute**.

---

### 2. Efficiency trade-offs

| Dimension | Dense Transformer | Mixture-of-Experts Transformer |
|---|---|---|
| **Parameters** | Total = active | Total > active |
| **Compute per token** | Fixed | Lower for same total parameter count |
| **Memory footprint** | Smaller | Much larger |
| **Training cost** | Simpler, more uniform | More complex routing and load balancing |
| **Inference throughput** | More predictable | Can be efficient if experts are well utilized |
| **Inference latency** | Easier to optimize | Can suffer from routing, communication, imbalance |
| **Scalability** | Capacity grows with compute | Capacity grows faster than active compute |

---

### 3. Compute efficiency

Dense models have a straightforward efficiency profile:

\[
\text{FLOPs per token} \propto \text{total parameters}
\]

So if you want more capacity, you must also increase per-token compute.

MoE models can have many more total parameters while keeping per-token compute lower:

\[
\text{FLOPs per token} \propto \text{active parameters}
\]

This means an MoE model can potentially:

- Store more knowledge.
- Specialize across different inputs.
- Achieve better quality per active FLOP.

But that benefit comes with trade-offs. The router adds overhead, and if experts are not well balanced, some experts may be overloaded while others sit idle.

---

### 4. Memory and storage trade-offs

MoE models usually require much more memory because all experts must be stored even if only a few are used per token.

For example:
- A 40B-parameter MoE model may require similar compute to a 10B dense model, but it still needs space for all 40B parameters.
- This can be problematic for:
  - Single-GPU inference.
  - Edge deployment.
  - Low-memory servers.

Dense models are simpler here: you store and use the same set of weights.

So MoE shifts the bottleneck from compute to memory and parameter storage.

---

### 5. Training trade-offs

Dense training is comparatively simple:
- Every parameter receives gradients for every token.
- Optimization is regular and well understood.

MoE training introduces new issues:
- **Routing**: The model must learn which expert to send each token to.
- **Load balancing**: If all tokens go to one expert, you waste capacity and create training instability.
- **Communication overhead**: In distributed training, expert parallelism can require sharding, all-to-all communication, and careful scheduling.
- **Sparse gradients**: Inactive experts may receive little or no gradient, making optimization more complex.

MoE training can still be very effective, but it is less “drop-in” than dense training.

---

### 6. Inference trade-offs

At inference time, MoE can be attractive because:
- You activate fewer parameters per token.
- Large models can be served with lower compute cost.

But it introduces systems complexity:
- **Expert parallelism**: experts may live on different devices.
- **Communication cost**: tokens must be routed to the right experts.
- **Batching behavior**: at low batch sizes, MoE can be inefficient because many experts are touched for few tokens.
- **Latency variance**: imbalance can cause some experts to become bottlenecks.

Dense models are usually easier to optimize for predictable latency and simpler deployment.

In high-throughput serving with large batches, MoE can be very efficient. In low-latency or single-stream inference, the overhead can be larger.

---

### 7. Quality and capacity trade-offs

One major motivation for MoE is that it can scale capacity without proportionally increasing compute:

- More experts = more total parameters.
- Same or similar active compute = lower FLOPs.

In practice, this often allows MoE models to outperform dense models of the same active size, or match larger dense models with lower compute.

However, MoE is not automatically better:
- It can be harder to train stably.
- It can underperform if routing is poor.
- It may require more data, tuning, and system engineering.

---

### 8. Core efficiency intuition

You can think of it this way:

- **Dense models** trade total capacity directly against compute.
- **MoE models** trade memory and systems complexity for compute efficiency.

A dense model is efficient in simplicity and predictability.  
An MoE model is efficient in compute scaling, but only if routing, load balancing, and serving infrastructure are handled well.

---

### 9. When each approach tends to make sense

**Dense transformers are preferable when:**
- You need predictable latency.
- Memory is limited.
- Deployment simplicity matters.
- You want a well-understood training/inference pipeline.

**MoE transformers are preferable when:**
- You want large capacity with limited active compute.
- You can afford higher memory.
- You have infrastructure for expert sharding and efficient routing.
- Your workload benefits from specialization across tokens.

---

### Bottom line

The main difference is that dense Transformers use the same weights for every token, while MoE models dynamically route tokens to a subset of experts. MoE therefore separates **total model size** from **per-token active compute**, enabling greater capacity at lower active compute cost. The trade-off is that MoE increases memory requirements, systems complexity, routing overhead, and load-balancing difficulty.
