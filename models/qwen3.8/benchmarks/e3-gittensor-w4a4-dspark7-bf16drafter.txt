Mixture-of-Experts (MoE) and dense transformers differ mainly in **how much of the model is computed for each token**.

### Dense transformer

In a dense transformer, every token passes through the same set of attention and feed-forward layers. In a typical decoder layer:

1. The token goes through self-attention.
2. The token goes through a feed-forward network (FFN).
3. Every weight in that layer is used for that token.

So:

- **Total parameters ≈ active parameters**
- **Compute per token is predictable**
- **Model size scales directly with compute cost**
- Training and inference are simpler and more uniform

This makes dense models easy to optimize, but if you want more model capacity, you usually have to pay for it with more compute.

---

### Mixture-of-Experts transformer

In an MoE transformer, some dense layers — usually the feed-forward layers — are replaced by multiple smaller “expert” networks. A router chooses which experts should process each token.

For example, a layer may have 32 experts, but each token only activates the top 1 or top 2.

So:

- **Total parameters are large**
- **Active parameters per token are smaller**
- **Compute per token is lower than a fully dense model of the same total size**
- **Model capacity can grow faster than per-token compute**

The key idea is:  
**MoE decouples total model size from per-token computation.**

---

### Efficiency trade-offs

| Aspect | Dense transformer | Mixture-of-Experts |
|---|---|---|
| **Parameter usage** | All parameters are active | Only a subset of experts is active per token |
| **Compute cost** | Scales with total parameter count | Scales mainly with active parameters, not total |
| **Model capacity** | Increases with active compute | Can increase total capacity while keeping active compute lower |
| **Memory footprint** | Stores and uses only the active model | Must store all experts; can be large |
| **Hardware efficiency** | Uniform, highly optimized matrix operations | Expert selection, routing, and variable loads can reduce hardware efficiency |
| **Training complexity** | Simpler | More complex: routing, load balancing, expert specialization |
| **Inference latency** | More predictable | May be lower FLOPs but can still be memory-bound or communication-bound |

---

### Main trade-offs

1. **More capacity, less compute**

   A large MoE model can have far more total parameters than a dense model but use only a small fraction per token. This can give better model quality at a similar inference compute budget.

2. **Total model size can be large**

   Even if only a few experts are active, all experts must usually be stored. That increases memory, checkpoint size, and sometimes serving cost.

3. **FLOPs savings do not always mean faster inference**

   MoE can reduce arithmetic operations, but transformers are often memory-bandwidth-bound at inference. Loading selected expert weights may still be expensive. So MoE may improve throughput without reducing latency as much as the FLOP reduction suggests.

4. **Communication overhead**

   In large distributed systems, MoE models often use expert parallelism. Tokens must be routed to the right experts, which can require expensive inter-GPU communication.

5. **Load balancing**

   If many tokens route to the same expert, some experts become bottlenecks. MoE systems need load-balancing losses, capacity constraints, or other mechanisms to keep experts utilized evenly.

6. **Batch size matters**

   MoE can be very effective at high batch sizes, where many tokens collectively activate many experts. At very small batch sizes, expert utilization may be poor and routing overhead becomes more significant.

---

### Bottom line

Dense transformers are simpler and more predictable: every token pays for the full model.  
MoE models are more efficient in compute-scaling terms: they allow a large total model to run with only a fraction of its parameters active per token.

The key efficiency trade-off is:

> **MoE improves compute efficiency and model capacity, but at the cost of larger total memory, routing complexity, load-balancing issues, and potentially lower hardware utilization.**
