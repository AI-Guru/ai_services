In a **dense transformer**, every token passes through the same feed-forward layers, so all parameters are used for every token. In a **mixture-of-experts** (`MoE`) transformer, the feed-forward layers are replaced by multiple “expert” sub-networks, and a router selects only a small subset of experts for each token.

The main efficiency trade-off is:

> **MoE decouples total model capacity from per-token compute cost, but increases memory, communication, and training/serving complexity.**

## Key architectural difference

| Aspect | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Feed-forward layer | One shared FFN per token | Multiple expert FFNs |
| Parameters activated per token | All parameters in that layer | Only top-1/top-2 experts per token |
| Total vs active parameters | Total = active | Total can be much larger than active |
| Routing | None | Gate/router chooses experts |
| Training complexity | Simpler | Requires load balancing, expert parallelism, capacity management |

A typical MoE model may have, for example, **30B total parameters** but only **3B–8B active parameters** per token.

## Efficiency trade-offs

### 1. Compute efficiency

A dense model’s compute cost scales roughly with its total parameter count. If you double the model size, you roughly double the FLOPs per token.

MoE can increase total capacity without proportionally increasing per-token compute:

```text
Dense:  FLOPs ≈ proportional to total parameters
MoE:    FLOPs ≈ proportional to active parameters
```

So for a fixed compute budget, an MoE model can often have more total parameters and potentially more knowledge capacity.

However, this does not always mean it is “better” for free. The model may need more training tokens to fully exploit the additional experts, and training stability becomes more sensitive to routing.

### 2. Memory efficiency

MoE models are usually **larger in total memory** than dense models with the same active compute budget.

For inference, you still need to store all experts unless you use caching, offloading, quantization, or sharding.

Example:

```text
Dense 7B model:  ~7B active parameters, ~7B parameters stored
MoE 30B/3B model: ~3B active parameters, ~30B parameters stored
```

The MoE model may cost similarly to a ~3B–6B dense model in per-token FLOPs, but it has a much larger memory footprint.

So MoE can trade **higher memory cost for lower active compute cost**.

### 3. Communication overhead

Dense models can be sharded or pipelined relatively straightforwardly. MoE models often require **expert parallelism**, where tokens must be routed to the workers holding their selected experts.

This introduces communication overhead:

```text
token dispatch → expert computation → token combine
```

Often this involves all-to-all communication across GPUs. The overhead can be significant, especially with:

- small batch sizes,
- large clusters,
- many experts,
- wide expert parallelism,
- high network latency.

Dense architectures avoid this routing traffic, making them simpler and often lower-latency.

### 4. Training complexity

Dense transformers have stable, predictable behavior: every token sees the same FFN.

MoE introduces routing, which creates additional challenges:

- **Load imbalance**: some experts receive many more tokens than others.
- **Capacity overflow**: a token’s selected expert may be full, requiring overflow handling or dropping.
- **Routing instability**: the gate may collapse onto a few experts.
- **Auxiliary losses**: MoE training often needs load-balancing losses to keep experts used evenly.
- **Data efficiency**: extra expert capacity may not translate directly into better quality unless the model is trained long enough.

These make MoE training more complex than dense training.

### 5. Serving and latency

Dense models are often simpler to serve:

- predictable latency,
- straightforward batching,
- no dynamic routing,
- no expert cache misses.

MoE inference can suffer from:

- routing overhead,
- dynamic token-to-expert dispatch,
- expert cache misses,
- higher memory bandwidth pressure,
- tail latency from uneven expert loads.

This can make MoE models less efficient in low-batch or latency-sensitive settings, even if their FLOPs per token are low.

## When each approach is preferable

### Dense transformers are generally better when:

- you want low complexity,
- you need low and predictable latency,
- memory is tight,
- batch sizes are small,
- deployment simplicity matters,
- you do not need a huge parameter pool at fixed compute.

### MoE is generally attractive when:

- you want more total capacity without increasing per-token FLOPs,
- you can afford higher memory storage,
- you have large batches to amortize communication,
- you can handle more complex training and serving infrastructure,
- you are optimizing for quality at a given compute budget rather than minimum memory.

## Bottom line

Dense transformers scale compute, memory, and capacity together. MoE separates them:

```text
Dense:  more capacity → more compute + more memory
MoE:    more capacity → more memory, but potentially similar active compute
```

The trade-off is not simply “MoE is more efficient.” Rather, MoE trades **memory, communication, routing, and training complexity** for the ability to have a larger total model while keeping per-token active compute lower.
