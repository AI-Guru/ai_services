A **dense transformer** processes every token through all active weights in each layer. A **mixture-of-experts (MoE)** model replaces parts of the network—usually the feed-forward layers—with multiple “expert” subnetworks, and a router selects only a subset of experts for each token.

The core efficiency trade-off is:

> **MoE trades lower per-token compute and more model capacity for higher total memory use, routing overhead, and system complexity.**

## 1. Parameter activation

### Dense transformer
Every token activates all parameters in the layer.

If a model has `P` parameters, then each token effectively uses roughly `P` parameters across the model, ignoring small differences from masks or layer types.

### Mixture-of-experts
Each token activates only a small subset of the experts.

For example, a MoE layer might have 64 experts, but each token uses only `top-2` or `top-8`. So:

- **Total parameters:** large, because many experts exist.
- **Active parameters per token:** much smaller, because only a few experts are used.

A common MoE pattern is:

> Many parameters, few active.

For example, a model may have 400B total parameters but only 30B active per token.

---

## 2. Compute cost

### Dense
Compute scales directly with total parameter count.

If you want a larger dense model, you usually need more FLOPs per token.

### MoE
MoE can increase model capacity without proportionally increasing compute per token.

Because only a subset of experts is active, the FLOPs are closer to the number of **active parameters**, not the total number of parameters.

So MoE can offer better **compute efficiency** when the goal is to increase model capacity without increasing inference or training compute proportionally.

However, there is still overhead:

- Router/gating computation.
- Load-balancing logic.
- Routing tokens to experts.
- Aggregating expert outputs.

This overhead is usually small compared with expert computation, but it matters in systems design.

---

## 3. Memory and storage

This is where MoE and dense differ most sharply.

### Dense
A dense model’s parameter count equals its active count.

So if a dense model has 70B parameters, it generally needs to store, load, and move roughly 70B parameters for inference or training, not counting optimizer states.

### MoE
MoE stores all experts, even though each token only uses a few.

This means:

- **Higher total weight memory.**
- **Higher training memory**, because gradients and optimizer states may be needed for all experts.
- **Potential offloading or sharding** during serving.
- **Higher memory bandwidth pressure** if experts are not resident in cache.

So MoE can be compute-cheap but memory-expensive.

In practical terms:

> MoE can look like a small model in compute, but like a large model in memory.

---

## 4. Training efficiency

### Dense
Training dense models is more straightforward:

- All parameters participate for every token.
- Parameter usage is uniform.
- Scaling behavior is well understood.
- No expert imbalance problem.

The trade-off is that increasing model size increases compute almost linearly.

### MoE
MoE can improve training efficiency by adding capacity without increasing active compute.

For example, a MoE model can have many more total parameters while maintaining the same active compute budget as a smaller dense model.

But training MoE models introduces new problems:

- **Load balancing:** Some experts may be used far more than others.
- **Expert undertraining:** If an expert is rarely selected, it may remain weak.
- **Capacity conflicts:** Too many tokens may be routed to popular experts.
- **Routing instability:** Early in training, gating can become unstable.
- **Batch size sensitivity:** MoE often needs enough tokens per step to keep all experts well used.

To mitigate this, MoE models often use techniques such as:

- Top-k gating.
- Auxiliary load-balancing losses.
- Expert capacity factors.
- Token dropping.
- Expert parallelism.
- Randomized routing during early training.

So MoE can be more parameter-efficient, but it is less training-stable than dense models at equal compute.

---

## 5. Inference and serving efficiency

### Dense
Dense models are simpler to serve:

- Fixed compute per token.
- Predictable latency.
- Easier memory footprint.
- Simpler hardware utilization.
- Less routing overhead.

But compute grows with model size.

### MoE
MoE can reduce FLOPs per token, but serving is more complex.

Advantages:

- Lower compute per token for large-capacity models.
- Can achieve better quality at a given active-compute budget.
- Can scale total parameters without linearly increasing inference FLOPs.

Disadvantages:

- Total weights are larger, so memory bandwidth becomes important.
- Experts must be distributed, cached, or offloaded.
- Token routing can create irregular memory access.
- Load imbalance across experts can cause some devices to be idle while others are busy.
- Latency can be less predictable if expert traffic is uneven.
- Small batches may not fully utilize all experts.

MoE serving often requires:

- Expert parallelism.
- All-to-all communication.
- Dynamic batching.
- Expert caching.
- Sharding of experts across GPUs or accelerators.

So MoE is often more **compute-efficient** but less **memory- and systems-efficient** unless the hardware and serving stack are designed for it.

---

## 6. Quality and scaling behavior

### Dense
Dense models have a well-understood scaling relationship:

- More parameters, more data, more compute → better quality.
- But the cost of increasing parameters is relatively direct.

### MoE
MoE can improve quality at a fixed active-compute budget because it adds conditional capacity.

This is useful when you want:

- A larger effective model.
- Better generalization.
- More specialized representations.
- Lower compute per token.

However, MoE quality depends heavily on:

- Number of experts.
- Top-k selection.
- Load balancing.
- Expert size.
- Training data distribution.
- Routing stability.
- Expert capacity.

If experts are undertrained or routing is poor, MoE may not deliver its full benefit. In other words:

> MoE can be more capacity-efficient, but only if the experts are well trained and well utilized.

---

## 7. Efficiency trade-off summary

| Aspect | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Active parameters | All parameters are active | Only selected experts are active |
| Compute per token | Proportional to total parameters | Closer to active parameters |
| Total memory | Lower for a given active size | Higher because all experts are stored |
| Training stability | More stable | Requires load balancing and careful routing |
| Inference simplicity | Simpler | More complex routing and expert sharding |
| Memory bandwidth | More predictable | Can be higher due to expert access |
| Scaling | Compute grows with model size | Capacity can grow faster than active compute |
| Best use case | Predictable, memory-constrained, simpler serving | Compute-constrained, large-capacity, expert-parallel systems |

---

## Intuition

A dense transformer is like a single fixed network where every token uses every weight.

A MoE is more like a network with many specialized subnetworks. Each token is sent to a few relevant experts. The model becomes larger overall, but each token still uses only a small part of it.

The efficiency trade-off is therefore:

- **Dense:** easier, more predictable, lower memory, but compute grows directly with model size.
- **MoE:** can achieve higher capacity at lower per-token compute, but requires more total memory, better load balancing, and more complex serving infrastructure.

In short:

> Dense transformers trade size for simplicity.  
> Mixture-of-experts trade memory and systems complexity for compute efficiency and capacity scaling.
