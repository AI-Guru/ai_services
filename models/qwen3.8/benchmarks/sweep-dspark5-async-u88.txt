Mixture-of-Experts (MoE) and dense transformer architectures differ mainly in **how many model parameters are activated for each token**. That single difference drives most of the efficiency trade-offs.

| Aspect | Dense Transformer | Mixture-of-Experts Transformer |
|---|---|---|
| Architecture | Every layer applies the same set of parameters to every token. | Certain layers, often feed-forward blocks, are replaced by multiple “experts”; a router selects a subset of experts per token. |
| Parameters per token | All parameters in each layer are used. | Only a subset of experts is active, e.g. top-1 or top-2 routing. |
| Total model size | Smaller for a given compute budget. | Can be much larger in total parameters while using fewer active parameters. |
| Training cost | Increases with total parameter count. | Can scale model capacity more cheaply in FLOPs, but requires careful load balancing and stability. |
| Inference cost | More predictable; all weights are used. | Lower active compute per token, but higher memory and communication overhead. |
| Suits | Latency-sensitive, simple deployment, stable training. | Large-capacity models where memory is manageable and parallelism is available. |

### Key trade-offs

1. **Capacity vs. compute**
   - Dense models: Increasing capacity usually means increasing FLOPs per token.
   - MoE models: You can add more expert parameters while keeping the number of active parameters per token relatively fixed.  
   - Example: A MoE model may have 100B total parameters but only activate 10B per token.

2. **Memory vs. active compute**
   - MoE reduces active compute, but all expert weights must usually be stored in memory or accessible somewhere.
   - This can make inference memory bandwidth-bound, especially if experts are not kept on fast memory.
   - Dense models use less total memory but do more computation per token.

3. **Latency and throughput**
   - Dense models have simpler, more regular execution, often making latency easier to predict.
   - MoE models can suffer from:
     - expert routing overhead,
     - uneven expert loads,
     - communication across devices in expert-parallel setups,
     - lower batch efficiency if routing creates sparse, irregular compute.
   - With good systems support, MoE can improve throughput on large clusters, but often at higher tail latency risk.

4. **Training complexity**
   - Dense transformers are easier to train stably.
   - MoE models require load-balancing losses, auxiliary routing objectives, careful initialization, and sometimes expert capacity limits. Poor routing can lead to “expert collapse,” where only a few experts are used.

5. **Scalability**
   - MoE is attractive for scaling: total parameter capacity can grow faster than per-token inference cost.
   - Dense scaling is simpler but more expensive per token as model size grows.

### Bottom line

Dense transformers favor **simplicity, predictability, and lower memory footprint**.  
MoE transformers favor **higher model capacity with lower active compute**, but trade that for **greater memory, communication, routing, and systems complexity**.
