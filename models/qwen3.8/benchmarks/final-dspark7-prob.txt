Mixture-of-Experts (MoE) and dense transformer architectures differ mainly in **whether every parameter is used for every token**.

## Dense transformers

In a dense transformer:

- Every token passes through the full model.
- Every layer, attention head, and feed-forward block is applied to every token.
- Model size directly determines compute cost:

\[
\text{FLOPs} \propto \text{number of parameters}
\]

So if you scale the model up, inference and training compute scale up roughly in proportion.

### Advantages

- Simple to train and serve.
- Predictable compute cost.
- Well-understood scaling behavior.
- Easier hardware optimization because the same parameters are used for all tokens.

### Disadvantages

- High compute cost for very large models.
- Less parameter capacity for a fixed inference FLOP budget.

---

## Mixture-of-Experts transformers

In an MoE transformer:

- Certain layers, often the feed-forward network, are replaced by multiple “expert” subnetworks.
- A router selects a small subset of experts, usually top-1 or top-2, for each token.
- Only the selected experts are activated for that token.

So an MoE model can have many total parameters but relatively few **active parameters** per token.

### Advantages

- **Sparsity**: total model capacity can grow without growing compute proportionally.
- **Efficiency at scale**: can approximate the quality of a larger dense model with lower active FLOPs.
- **Flexible scaling**: you can add more experts to increase capacity without forcing every token to use all of them.

### Disadvantages

- Higher total memory footprint because all experts must be stored.
- Routing overhead and load-balancing complexity.
- Training can be less stable and more data-hungry.
- Inference can be less predictable due to variable expert usage.
- Often needs expert parallelism or sharding, adding communication overhead.

---

## Key efficiency trade-offs

| Aspect | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Parameters used per token | All parameters | Only a subset of experts |
| Compute scaling | Scales with total model size | Can scale total params with slower active compute growth |
| Inference FLOPs | High for large models | Lower active FLOPs, but routing/memory overhead exists |
| Memory | Lower for same active compute | Higher total memory due to all experts |
| Training | Simpler and more stable | More complex due to routing and load balancing |
| Serving | Predictable latency | Latency can vary with batch size and expert utilization |
| Hardware fit | Very hardware-friendly | Benefits from expert parallelism but introduces communication costs |

---

## In practice

A MoE model can be attractive when you want:

- A large total model capacity,
- But only a moderate amount of active compute per token.

For example, a MoE model might have 100B total parameters but only 10–20B active parameters per token. This can give strong model quality while reducing the forward-pass compute compared to a fully dense 100B model.

However, the efficiency gain is not free. MoE systems introduce:

- Routing cost,
- Load-balancing losses,
- Expert memory pressure,
- All-to-all communication in distributed settings,
- More complex batching and caching.

So the main trade-off is:

> **MoE trades architectural simplicity and predictable compute for sparsity, allowing larger model capacity at lower active compute cost.**

Dense models remain simpler and easier to serve, while MoE models can offer better capacity-per-FLOP if the added complexity and infrastructure overhead are manageable.
