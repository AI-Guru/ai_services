Mixture-of-Experts (MoE) and dense transformers differ mainly in how they allocate compute across tokens. A dense transformer applies the same feed-forward network (FFN) to every token, while an MoE transformer routes each token to a small subset of specialized “expert” FFNs.

## Core architectural difference

### Dense transformer
- Each layer has one FFN.
- Every token goes through the full FFN.
- Compute is uniform: all parameters in the FFN are active for every token.

At layer `i`, a token typically does:

```text
Attention(token) + FFN(token)
```

All FFN weights are used for every token.

### Mixture-of-Experts transformer
- The FFN layer is replaced by many expert FFNs.
- A lightweight router selects a small subset of experts, e.g. top-1 or top-2.
- Only the selected experts are activated for that token.

Conceptually:

```text
Attention(token) + Expert1(token) + Expert2(token)
```

But the model stores all experts and chooses only a few per token.

The key idea is **parameter sparsity**: the model can have many total parameters, but only a fraction are active per token.

---

## Efficiency trade-offs

| Dimension | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Total parameters | All parameters active per token | Usually much larger total parameter count |
| Active parameters per token | High | Lower, because only a few experts are selected |
| Compute per token | Higher | Lower, if sparsity is high |
| Memory footprint | Smaller, because fewer weights are stored | Larger, because all experts must be stored |
| Training complexity | Simpler and more predictable | More complex due to routing, load balancing, expert parallelism |
| Inference hardware utilization | Generally better and more uniform | Can be lower due to variable expert usage and communication |
| Scaling behavior | Compute grows directly with active parameter count | Can increase model capacity without proportionally increasing compute |

---

## Compute trade-off

A dense transformer with a large FFN pays the full FFN cost for every token. If you want a larger FFN, the cost per token increases directly.

An MoE model can store many experts but activate only a few. For example, a model might have 64 experts per layer but use only top-2. The active parameter count can be far smaller than the total parameter count.

This gives MoE a major advantage: it can have high capacity while keeping per-token compute lower than a dense model of the same total size.

In rough terms:

```text
Dense:   larger model => larger compute per token
MoE:     larger model => more stored knowledge, but not all knowledge is used every token
```

So MoE can improve the capacity-compute trade-off: you get a larger model without a proportional increase in FLOPs per token.

---

## Memory trade-off

MoE’s biggest drawback is memory.

Even though only a few experts are active per token, the model must usually keep all expert weights in memory. This matters because inference serving is often limited by memory bandwidth and GPU memory capacity, not just compute.

A dense model with 10B active parameters may be stored in a relatively straightforward way. An MoE model with 10B active parameters might have 50B, 100B, or more total parameters, all of which need to be resident on the accelerator unless expert offloading or quantization is used.

So MoE often trades compute efficiency for memory efficiency.

A typical MoE trade-off is:

```text
More total parameters
Fewer active parameters
Lower per-token compute
Higher memory footprint
```

---

## Inference efficiency

For inference, MoE can be attractive when the main constraint is per-token compute rather than memory bandwidth.

Because only a subset of experts is active, the arithmetic cost per token can be lower. This can be useful for large-scale serving where you want high capacity but controlled inference cost.

However, MoE inference has additional overhead:

- Routing every token to experts
- Gather/scatter operations for expert activations
- Uneven expert load
- Expert parallelism across multiple accelerators
- All-to-all communication in distributed settings
- Potential expert memory footprint that exceeds available accelerator memory
- Caching and quantization complexity

A dense model has simpler, more predictable inference behavior. Every token does the same amount of work, which is easier for hardware schedulers and memory systems.

MoE can be more efficient in FLOPs, but not always in wall-clock latency or memory bandwidth.

---

## Training efficiency and stability

Training MoE models is more complex than training dense models.

The main issues are:

1. **Routing**
   The model must learn a gating function that sends tokens to useful experts. Poor routing can waste capacity.

2. **Load balancing**
   Some experts may become overloaded while others are underused. Models often use auxiliary load-balancing losses, expert capacity limits, or expert dropping.

3. **Training instability**
   MoE models can be harder to train stably, especially early in training, because router decisions and expert specialization interact.

4. **Distributed communication**
   Expert parallelism requires moving tokens to the appropriate expert across devices. This adds communication overhead.

5. **Optimizer memory**
   Even if only some experts are updated per token, many training setups still store optimizer states for all expert parameters, increasing memory usage.

Dense transformers avoid most of these issues. Their training pipeline is simpler, easier to parallelize, and generally more predictable.

---

## Specialization vs. uniformity

A dense FFN is a single shared function. Every token is processed by the same weights.

MoE experts can specialize. Different experts may become better at different token types, linguistic patterns, modalities, tasks, or computational regimes.

This can improve representation capacity: the model can store more diverse information without every token paying for all of it.

The trade-off is that specialization is not automatic. It depends on routing quality, expert capacity, training stability, and serving configuration.

---

## Practical efficiency comparison

### Dense is usually better when:
- The model is small to medium-sized.
- Simplicity matters.
- Memory is limited.
- Inference latency must be highly predictable.
- Hardware utilization is critical.
- Expert parallelism is too costly.
- The deployment environment cannot easily handle large sparse model weights.

### MoE is usually better when:
- You need very high capacity at a controlled per-token compute budget.
- You can store a large model in accelerator memory.
- You can use expert parallelism efficiently.
- You want to scale knowledge without scaling active compute linearly.
- The application benefits from specialized experts.
- You can tolerate more complex training and serving infrastructure.

---

## Short version

A dense transformer spends all its FFN compute on every token. It is simpler, more predictable, and usually more memory-efficient for a given active size.

A mixture-of-experts transformer stores many experts but activates only a few per token. This can increase model capacity while keeping active compute low, but it increases memory pressure, routing complexity, training difficulty, and communication overhead.

In short:

```text
Dense:    uniform compute, simpler, lower memory for a given active size
MoE:      sparse compute, larger capacity, higher memory and systems complexity
```

MoE is most useful when you want the knowledge of a large model with the per-token cost of a smaller one.
