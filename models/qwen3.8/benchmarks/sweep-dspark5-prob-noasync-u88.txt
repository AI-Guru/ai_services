Mixture-of-experts (MoE) and dense transformer architectures differ mainly in how they allocate model capacity. A dense transformer applies the same set of weights to every token, while an MoE model routes each token to a subset of specialized sub-networks, typically “experts,” activating only a fraction of the total parameters.

## Core architectural difference

### Dense transformer

In a standard dense transformer, each layer usually contains:

- self-attention
- feed-forward network
- layer normalization
- residual connections

For every token, the model processes the full feed-forward network.

If a layer has parameter count \(P\), then every token uses those \(P\) parameters. Total compute scales directly with total parameter count.

Example:

- Total parameters: 7B
- Active parameters per token: 7B
- Compute cost: proportional to 7B

Dense models have a uniform computation path: every token goes through the same layers.

---

### Mixture-of-experts transformer

In an MoE model, parts of the network — often the feed-forward blocks — are replaced with multiple expert networks. A lightweight router decides, for each token, which experts to use.

For example, an MoE layer might contain 8 experts but only route each token to the top 2.

Example:

- Total parameters: 100B
- Active parameters per token: 10B
- Compute cost: roughly proportional to 10B active parameters, not 100B

This creates a gap between:

- **Total parameter count**: large model capacity
- **Active parameter count**: smaller per-token compute cost

That separation is the main appeal of MoE.

---

# Key efficiency trade-offs

## 1. Compute efficiency

### Dense models

Dense models use all parameters for every token. Their compute cost is predictable and directly tied to parameter count.

If you increase model size, compute cost increases proportionally.

This makes dense models straightforward to plan:

\[
\text{Compute} \propto \text{total parameters}
\]

### MoE models

MoE models can have many more total parameters while using only a subset per token. This can give better model quality for the same active compute budget.

For example, a model may have 100B total parameters but only activate 10B per token. It can behave more like a large model in capacity while paying closer to the compute cost of a much smaller dense model.

So MoE can improve **quality-per-FLOP** or **quality-per-active-compute**.

However, “active compute” is not the only cost. Routing, memory access, load balancing, and expert communication add overhead.

---

## 2. Memory footprint

### Dense models

A dense model stores all parameters in memory. If a model has 70B parameters, the weights alone must fit in accelerator memory, possibly split across many devices.

Inference memory cost is dominated by the total parameter count.

### MoE models

MoE models can have much larger total parameter counts than dense models of the same active compute size. That increases memory requirements.

For example:

| Model type | Total parameters | Active parameters | Memory pressure |
|---|---:|---:|---|
| Dense | 10B | 10B | Moderate |
| MoE | 50B | 10B | Higher |

The MoE model may have lower compute per token, but it may require much more memory because all experts must be available.

This is a central trade-off:

> MoE trades memory and infrastructure complexity for lower per-token compute.

---

## 3. Inference latency and throughput

### Dense models

Dense inference has a simple data path. For modern hardware, dense matrix multiplications are well optimized and highly parallel.

Latency is usually relatively predictable, especially at low batch sizes.

### MoE models

MoE inference has extra costs:

- Router computation
- Expert selection
- Dispatching tokens to experts
- Expert-specific computation
- Combining expert outputs
- Balancing expert load

These operations can reduce hardware efficiency, especially on GPUs, because experts are accessed in a sparse, irregular pattern.

MoE models can be very efficient at high batch sizes, because experts can be reused across many tokens. But they may be less efficient at very small batch sizes or low-throughput interactive settings.

So the efficiency gain from MoE depends heavily on deployment regime:

| Deployment setting | Dense | MoE |
|---|---|---|
| Low-batch interactive inference | Often simpler and more efficient | Can suffer from expert memory and dispatch overhead |
| High-batch server inference | High compute cost | Can amortize expert costs and gain efficiency |
| Long-context inference | Predictable | May increase memory and routing complexity |
| Fine-tuning or on-device | Often easier | More complex unless experts are heavily pruned or specialized |

---

## 4. Training efficiency

### Dense models

Training a dense model is conceptually straightforward:

- Forward pass uses all parameters.
- Backward pass updates all parameters.
- Optimizer states scale with total parameter count.

The main trade-off is simple: larger model = higher compute and memory.

### MoE models

MoE training can offer better scaling behavior in some regimes. A model can have large total capacity without paying full dense compute cost for every token.

However, MoE introduces training complications:

- Router instability
- Expert under-utilization
- Load imbalance
- Need for auxiliary load-balancing losses
- Sensitivity to hyperparameters
- Potential for expert collapse, where many tokens route to the same expert
- More complex distributed training
- Additional communication between experts and devices

A well-trained MoE model can be very efficient, but it is harder to train reliably than a dense model.

---

## 5. Hardware utilization

### Dense models

Dense transformers are highly amenable to modern accelerators. Large dense matrix multiplications map well to tensor cores, and memory access patterns are regular.

This makes dense models easier to accelerate.

### MoE models

MoE models are more irregular. Different tokens are sent to different experts, which can cause:

- irregular memory access
- uneven GPU utilization
- poor occupancy in some expert shards
- need for specialized MoE kernels
- complex inter-device communication

Highly optimized MoE systems can recover much of the efficiency gain, but baseline implementations may underperform.

In practice, MoE efficiency is strongly system-dependent.

---

## 6. Capacity and generalization

### Dense models

Dense models distribute capacity evenly. Every part of the network participates in every token’s computation.

This makes them simpler and more uniformly utilized, but it can limit the amount of capacity that can be added without a proportional compute increase.

### MoE models

MoE models can store more capacity by having many experts. Different experts can specialize:

- by domain
- by token type
- by linguistic pattern
- by task-relevant features
- by data regime

This can improve representational capacity without increasing per-token active compute.

However, specialization can also introduce issues:

- Some experts may become redundant.
- Some experts may be undertrained.
- The model may become more brittle if routing degrades.
- Fine-tuning one domain can affect routing and expert balance.

---

## 7. Cost breakdown

A useful way to think about the trade-off is to separate three quantities:

### Total parameters

This affects:

- memory footprint
- model storage
- checkpoint size
- expert-parallelism requirements

### Active parameters

This affects:

- per-token compute
- FLOPs
- theoretical throughput

### System overhead

This affects:

- actual latency
- GPU utilization
- training stability
- serving complexity

Dense models have:

- active parameters = total parameters
- low routing overhead
- high hardware utilization
- simpler systems

MoE models have:

- active parameters < total parameters
- higher memory footprint
- extra routing and dispatch overhead
- potentially better quality for a given active compute
- more complex training and serving

---

# Summary comparison

| Aspect | Dense transformer | Mixture-of-experts |
|---|---|---|
| Parameter usage | All parameters used per token | Only a subset of experts used per token |
| Total capacity | Limited by active compute | Can store more total capacity |
| Per-token compute | Proportional to total size | Proportional to active parameters |
| Memory cost | Higher as total size grows | Can be very high due to many experts |
| Training complexity | Simpler | More complex, needs load balancing and routing stability |
| Inference simplicity | Simpler | More complex, with routing and expert dispatch |
| Hardware efficiency | Strong, predictable | Depends on batching, expert parallelism, and implementation |
| Scaling behavior | Larger = higher compute | Can scale capacity more efficiently, but with system overhead |
| Best use case | Simplicity, strong baseline, low-latency serving | Large-capacity models where active compute must be controlled |

---

# Main efficiency trade-off in one sentence

Dense transformers are simpler and more hardware-efficient per operation, but every increase in model size increases both memory and compute; MoE transformers can have much larger total capacity while using only a fraction of those parameters per token, gaining compute efficiency at the cost of higher memory, routing complexity, load-balancing difficulty, and system overhead.
