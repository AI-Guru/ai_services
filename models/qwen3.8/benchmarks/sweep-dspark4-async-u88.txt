The core difference is **how much of the model is used for each token**.

## 1. Dense transformer: uniform compute

In a standard dense transformer, every token passes through the same full model:

- every attention layer is applied to every token,
- every MLP/FFN layer is applied to every token,
- all non-embedding parameters are active during inference.

If the model has \(P\) parameters, both:

- per-token compute, and
- weight memory footprint

scale roughly with \(P\).

That makes dense models simple and predictable, but also means that increasing model capacity directly increases compute cost per token.

---

## 2. Mixture-of-Experts: conditional compute

A Mixture-of-Experts, or MoE, transformer replaces some dense layers, usually the FFN/MLP layers, with multiple “expert” subnetworks and a learned router.

For each token, the router selects a small subset of experts, often the top \(k\) experts:

\[
\text{total params} = P_{\text{total}}
\]

\[
\text{active params per token} = P_{\text{active}}
\]

Usually:

\[
P_{\text{total}} \gg P_{\text{active}}
\]

For example, a MoE model might have 1 trillion total parameters but only 8 billion active parameters per token.

The key architectural difference is therefore:

> **Dense models scale compute and memory together. MoE models decouple stored capacity from active compute.**

---

# Main efficiency trade-offs

## 1. Compute vs memory

A dense model’s cost is relatively straightforward:

\[
\text{compute per token} \propto P
\]

\[
\text{weight memory} \propto P
\]

A MoE model separates those two:

\[
\text{compute per token} \propto P_{\text{active}}
\]

\[
\text{weight memory} \propto P_{\text{total}}
\]

So MoE models can store much more capacity while executing fewer operations per token.

Example:

| Model type | Total params | Active params per token | Compute cost |
|---|---:|---:|---:|
| Dense 8B | 8B | 8B | ~8B |
| Dense 1T | 1T | 1T | ~1T |
| MoE 1T total / 8B active | 1T | 8B | ~8B |

The MoE model has the memory footprint of the 1T dense model but the per-token compute cost of the 8B dense model.

That is the central efficiency win: **more capacity without proportional compute**.

But the trade-off is that MoE models require storing many more weights than they actually use per token.

---

## 2. Inference throughput depends heavily on batch size

MoE models are most efficient when many tokens can share the same expert weights within a batch.

For a single token, or a very small batch:

- only a few experts are active,
- but the system may still need to manage many total experts,
- routing, dispatch, and expert selection add overhead,
- kernels are less regular than dense GEMM kernels,
- GPU utilization may be lower.

For large batches:

- expert weights are reused across many tokens,
- compute is better amortized,
- batching improves memory and bandwidth efficiency.

So MoE inference efficiency is strongly batch-size dependent.

A dense model is usually more consistent and easier to serve at small batch sizes or for latency-sensitive requests. A MoE model can be very efficient at high-throughput serving, assuming the system is designed to exploit expert reuse.

---

## 3. MoE reduces active FLOPs, but not all compute

MoE usually sparsifies the FFN/MLP layers.

However, attention layers are often still dense and applied to every token.

Therefore, the compute savings from MoE are mainly in the feed-forward portion of the model.

For short sequences where the FFN dominates, MoE can give large compute savings.

For long-context LLMs where attention dominates, the relative efficiency gain is smaller because attention still scales with sequence length and token count.

So:

- MoE helps when FFN/MLP compute is a major cost.
- MoE helps less when attention is the dominant cost.

---

## 4. Weight memory is the major downside

Because MoE models have many experts, their total parameter count can be very large.

That means:

- larger model files,
- larger GPU memory requirements,
- larger optimizer state memory during training,
- potentially more complex sharding, offloading, or quantization.

A dense model’s memory requirement is easier to estimate:

\[
\text{memory} \approx \text{number of active parameters}
\]

For MoE:

\[
\text{memory} \approx \text{number of total parameters}
\]

Even though only a subset is active per token, all experts must generally be available during inference.

Thus, MoE trades compute efficiency for increased storage and system complexity.

---

## 5. Training is less straightforward

Dense transformers are easier to train because every token updates the same full network.

MoE introduces several additional training challenges:

### Expert load imbalance

If the router sends most tokens to a few experts, those experts may become overused while others are undertrained.

This can cause:

- uneven expert utilization,
- degraded model quality,
- wasted capacity,
- instability during training.

Common fixes include:

- auxiliary load-balancing losses,
- expert biasing,
- token dropping,
- capacity factors.

### Capacity factor

Each expert often has a fixed capacity, meaning it can process only a limited number of tokens per layer.

If too many tokens are routed to one expert, some tokens may be dropped or the capacity factor must be increased.

Dropping tokens can introduce bias and hurt quality. Increasing capacity factor increases memory and compute, reducing some of MoE’s efficiency advantages.

### Expert parallelism

In large-scale training, experts are often sharded across GPUs.

This requires communication between devices, usually via all-to-all dispatch and combine operations.

That adds overhead compared with dense model parallelism.

### Expert undertraining

Because each expert sees only a subset of tokens, some experts may receive fewer gradient updates than a dense model’s corresponding layer would.

This is not necessarily bad if the dataset is large enough, but it does mean that MoE scaling is not a free lunch:

\[
\text{lower per-token FLOPs} \neq \text{same effective training quality for free}
\]

MoE can improve scaling efficiency, but it requires careful tuning.

---

## 6. Router overhead

MoE models add a routing mechanism.

For each token, the system must:

1. compute router scores,
2. select the top \(k\) experts,
3. route the token to those experts,
4. combine the expert outputs.

The router itself is usually cheap, but token routing, sorting, dispatch, and gather/scatter operations are more irregular than dense matrix multiplications.

This makes MoE less GPU-friendly in some settings, especially on single-device inference or small models.

Dense models benefit from highly optimized, regular kernels. MoE performance often depends more on system design.

---

## 7. Capacity vs active compute

MoE models allow a model to store more “knowledge” or capability than would be possible for the same active compute budget.

This can be especially useful for:

- large language models,
- multimodal models,
- knowledge-intensive tasks,
- long-tail or specialized behaviors.

However, having more total parameters does not automatically mean proportional quality gains.

The practical trade-off is:

- **Dense model:** every parameter contributes to every token.
- **MoE model:** many parameters are available conditionally, but each token only uses a few.

MoE can improve quality per active FLOP, but returns may diminish if:

- active compute is too small,
- experts are poorly utilized,
- routing is weak,
- total capacity is wasted on redundant experts.

---

# Summary table

| Aspect | Dense transformer | Mixture-of-Experts |
|---|---|---|
| Parameter usage | All params active per token | Only selected experts active per token |
| Compute scaling | Scales with total params | Scales mainly with active params |
| Memory scaling | Scales with total params | Scales with total params, including inactive experts |
| Simplicity | Simple, mature kernels | More complex routing and dispatch |
| Inference efficiency | Predictable, good at small batch | Can be very efficient at high batch, less so at low batch |
| Memory footprint | Lower for same active compute | Higher total weight footprint |
| Training stability | Generally more stable | Requires load balancing and capacity management |
| Communication | Simpler parallelism | Expert parallelism and all-to-all communication |
| Quality scaling | More params = more compute | More params can improve quality without proportional compute |
| Best use case | Simpler, smaller, latency-sensitive, memory-constrained | Large capacity, high-throughput, compute-budget-constrained systems |

---

# Bottom line

Dense transformers have a simple efficiency relationship:

\[
\text{more parameters} \Rightarrow \text{more compute and memory}
\]

MoE transformers break that relationship:

\[
\text{more parameters} \not\Rightarrow \text{proportional compute increase}
\]

The main trade-off is:

> **MoE models can be much more compute-efficient for a given amount of stored capacity, but they require more total memory, more complex systems, careful load balancing, and favorable batching or parallelism conditions.**

Dense models are simpler and more predictable. MoE models can deliver better scaling efficiency, but only if the hardware, batch size, and training strategy are suitable for sparse expert activation.
