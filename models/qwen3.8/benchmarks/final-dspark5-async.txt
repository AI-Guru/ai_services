A **dense transformer** applies the same full feed-forward network to every token, so the number of weights in the model is essentially the number of weights activated per token.

A **mixture-of-experts (MoE)** transformer replaces one large feed-forward layer with multiple smaller “expert” subnetworks plus a router. For each token, the router selects a small subset of experts, usually top-1 or top-2, and only those experts compute a result for that token.

The core efficiency difference is:

> **MoE decouples total parameter count from active compute.**  
> A model can store many experts, but activate only a small subset per token.

That trade-off creates several important efficiency consequences.

---

## 1. Compute: MoE can be faster per token, but not automatically

For a dense transformer with \(P\) parameters, roughly \(P\) weights are used for each token.

For a MoE model:

\[
P_{\text{total}} = P_{\text{base}} + E \cdot P_{\text{expert}}
\]

\[
P_{\text{active}} = P_{\text{base}} + k \cdot P_{\text{expert}}
\]

where:

- \(E\) = number of experts  
- \(k\) = number of experts selected per token  
- \(P_{\text{base}}\) = non-expert parameters such as attention, norms, embedding, output heads  

If \(k < E\), then:

\[
P_{\text{active}} < P_{\text{total}}
\]

So MoE can provide much larger model capacity with lower per-token FLOPs than a dense model of the same total size.

### Example

Suppose a model has 8 experts, each 5B parameters, and selects top-2 experts.

- Total expert parameters: \(8 \times 5B = 40B\)
- Active expert parameters: \(2 \times 5B = 10B\)

The model may behave more like a much larger dense model in terms of capacity, but only performs the compute of a smaller dense model per token.

### But there are overheads

MoE is not simply “more parameters, same compute.” It adds:

- Router computation
- Token-to-expert dispatch
- Expert-to-token gathering
- Load-balancing logic
- Extra memory traffic
- Possible capacity overflow or token dropping
- Communication overhead in distributed settings

So the practical speedup may be smaller than the theoretical FLOP reduction.

---

## 2. Memory: MoE uses much more memory

This is the biggest trade-off.

A dense model stores only the weights it actively uses.

A MoE model stores **all experts**, even if most are inactive for a given token.

That means:

| Property | Dense | MoE |
|---|---:|---:|
| Total weights stored | Smaller | Larger |
| Active weights per token | All weights | Only selected experts |
| Memory pressure | Lower | Higher |
| Optimizer state memory | Proportional to active weights | Proportional to all expert weights |

For inference, MoE often requires all expert weights to be resident on GPU, unless experts are offloaded to CPU or NVMe. If offloaded, the model may be slower due to memory bandwidth and transfer latency.

For training, MoE requires optimizer states for all experts, even though only some experts are active for each token. This increases memory substantially unless expert weights and optimizer states are sharded across devices.

So MoE trades **memory efficiency** for **compute efficiency**.

---

## 3. Hardware utilization: dense is usually easier to execute efficiently

Dense transformers are highly regular. Each token goes through the same layers, producing predictable matrix multiplications that are very well optimized for GPUs and TPUs.

MoE is more irregular:

- Each token may route to different experts.
- Expert loads may be uneven.
- Some experts may receive many more tokens than others.
- Expert GEMMs can be smaller and less efficient.
- Batched token-to-expert dispatch can fragment workloads.
- GPU utilization may be lower if experts are too small or if the batch size is small.

This is especially important for inference:

- Dense models have predictable latency and throughput.
- MoE models can be more sensitive to batch size and routing behavior.
- Small-batch inference may underuse experts because different tokens select different experts.
- Large-batch serving can improve expert utilization because tokens are spread across experts.

In other words, MoE can be compute-efficient in theory, but dense models often have better **hardware efficiency** in practice.

---

## 4. Communication: MoE is harder to scale across devices

Dense transformers are commonly parallelized using tensor parallelism or pipeline parallelism. The communication patterns are relatively standard and predictable.

MoE often uses **expert parallelism**, where different experts are placed on different devices. For each token, the system must route tokens to the devices that hold their selected experts.

This introduces:

- All-to-all communication
- Token shuffling
- Dynamic load imbalance
- Possible tail latency
- More complex scheduling

If experts fit on a single GPU, MoE is simpler, but memory may be the bottleneck. If experts are sharded across many GPUs, communication can become a major cost.

So MoE can reduce active compute, but it may increase communication and systems complexity.

---

## 5. Training complexity: MoE requires careful stabilization

Dense transformers are simpler to train: all tokens use the same feed-forward weights, and there is no routing decision.

MoE requires additional machinery:

- Learned router
- Top-k gating
- Load-balancing auxiliary loss
- Expert capacity limits
- Token dropping or expert queuing when capacity is exceeded
- Expert utilization monitoring
- Careful batch-size and data-scaling choices

Problems include:

- Router collapse: one or a few experts become overly popular.
- Expert underuse: some experts receive too few tokens and learn poorly.
- Capacity overflow: many tokens route to the same expert.
- Instability: aggressive load-balancing losses can hurt quality.
- Sensitivity to batch size: MoE usually benefits from larger batches because expert load averages out.

Thus, MoE can be harder to train stably and may require more tuning.

---

## 6. Quality versus efficiency: MoE can buy quality with less active compute

The main advantage of MoE is that it can often approach the quality of a larger dense model while using fewer active FLOPs per token.

For example:

- A 30B active-parameter MoE model may have 200B+ total parameters.
- It may outperform a 30B dense model in many benchmarks.
- It does so with roughly the same per-token compute as a 30B dense model, but with more stored capacity.

However, that quality gain is not free. It comes with:

- Higher memory usage
- More complex inference systems
- Potentially lower GPU utilization
- More training instability
- Greater sensitivity to routing and load balancing

So MoE is a **capacity-for-compute trade-off**: you get more model capacity per active FLOP, but you pay in memory, systems complexity, and sometimes efficiency.

---

## 7. Batch-size sensitivity

Dense models are relatively insensitive to batch size in terms of which weights are active. Every token uses the same full network.

MoE benefits more from larger batches because:

- More tokens spread over experts smooths load imbalance.
- Experts receive enough tokens to be utilized efficiently.
- Communication overhead can be amortized.
- Training is more stable.

With small batches or short sequences, MoE can be less efficient because:

- Fewer tokens reach each expert.
- Expert utilization is uneven.
- Dispatch overhead is less amortized.
- Inference latency may increase.

This is one reason MoE often performs better in large-batch serving or training settings.

---

## 8. Attention is not automatically improved

Most MoE architectures change the feed-forward block, not the attention mechanism.

Therefore:

- Attention remains dense in standard MoE transformers.
- The quadratic cost of attention with respect to sequence length is unchanged.
- For very long contexts, attention may dominate compute, reducing the relative benefit of MoE.

MoE mainly improves efficiency of the feed-forward portion of the transformer, not the attention portion.

---

## Summary table

| Dimension | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Parameter usage | All parameters active per token | Only selected experts active |
| Total parameters | Smaller | Much larger possible |
| Active FLOPs | Scales with total parameters | Scales with active experts |
| Memory usage | Lower | Higher |
| Training memory | Lower | Higher due to all experts and optimizer states |
| Inference memory | Lower | Higher, unless experts are offloaded/quantized |
| Hardware efficiency | High, regular, well optimized | Lower, irregular, expert-dependent |
| Serving complexity | Simpler | More complex routing and expert placement |
| Communication overhead | Lower | Higher with expert parallelism |
| Load balancing | Not needed | Required |
| Training stability | More stable | More sensitive to routing, capacity, batch size |
| Batch-size sensitivity | Lower | Higher |
| Main trade-off | Simpler and memory-efficient, but less capacity per FLOP | More capacity per FLOP, but more memory and systems cost |

---

## Bottom line

A dense transformer is straightforward: you pay memory and compute proportional to the number of parameters.

A mixture-of-experts model is more nuanced:

> MoE can achieve high model capacity with lower active compute, but it trades that compute efficiency for increased memory, communication, training complexity, and systems overhead.

MoE is most attractive when:

- You can afford storing many parameters.
- You have enough batch size or serving load to use experts efficiently.
- You can handle expert parallelism or memory pressure.
- You want higher model quality without proportionally higher per-token compute.

Dense transformers are usually better when:

- Simplicity matters.
- Memory is limited.
- Inference latency must be predictable.
- Batch sizes are small.
- Hardware utilization and optimized dense kernels are more important than parameter scale.
