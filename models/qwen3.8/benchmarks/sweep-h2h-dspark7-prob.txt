Mixture-of-Experts (MoE) and dense transformer architectures differ mainly in how they allocate and activate model capacity.

## Core architectural difference

### Dense transformer
In a standard dense transformer, every token in a layer passes through the same feed-forward network or attention-related submodules.

For each token, all parameters in the relevant layer are used.

If the model has \(P\) parameters, then approximately all \(P\) parameters contribute to each forward pass, at least in the sense that each token updates/reads the full dense weights for its layer.

### Mixture-of-Experts
In an MoE layer, instead of one dense feed-forward block, there are multiple expert networks, often small feed-forward blocks. A router selects the top-\(k\) experts for each token.

For example:

- 8 experts total
- each token uses 2 experts

Then the model has much larger total parameter count, but each token only activates a fraction of those parameters.

So MoE separates:

- **Total model size**: number of stored weights
- **Active compute per token**: number of weights actually used for a given token

---

# Key efficiency trade-offs

## 1. Parameter count vs. active compute

A dense model’s parameter count is roughly equal to the number of parameters used per token.

An MoE model can have:

- many more total parameters,
- but fewer or comparable active parameters per token.

Example:

| Architecture | Total experts | Experts used per token | Relative active compute |
|---|---:|---:|---:|
| Dense FFN | 1 | 1 | baseline |
| MoE with 8 experts, top-2 | 8 | 2 | higher than dense if experts are small |
| MoE with 64 experts, top-2 | 64 | 2 | active compute controlled, total capacity much larger |

This allows MoE models to store more knowledge or capability without proportionally increasing per-token FLOPs.

### Trade-off
You can scale capacity more efficiently than a dense model, but the benefits depend on how you measure efficiency:

- **FLOPs per token**: can be controlled
- **memory footprint**: grows with total expert count
- **training cost**: grows with number of expert parameters that receive gradients
- **inference cost**: can be low in FLOPs but high in memory bandwidth or expert scheduling complexity

---

## 2. Memory requirements

MoE models have a larger total parameter count because all experts must be stored, even though only some are used per token.

This affects two different settings:

### Training memory
During training, all experts may receive gradients, so the optimizer state and activation memory increase substantially.

A dense model with \(P\) active parameters requires optimizer state for roughly those \(P\) parameters.

An MoE model may have \(10P\) or \(100P\) total parameters, depending on the number of experts, even if only \(2P\) are active per token.

So MoE training is more memory-intensive and harder to scale.

### Inference memory
At inference, you must store all expert weights. If experts fit on the same device, serving can be fast. If they do not fit, you may need:

- model sharding across GPUs
- expert offloading to CPU or slow memory
- dynamic routing across devices
- additional communication overhead

This can reduce the practical efficiency gains.

### Trade-off
MoE can increase model capacity without increasing per-token compute, but it increases stored model size. This is useful when the bottleneck is compute rather than memory, less useful when the bottleneck is memory bandwidth.

---

## 3. Compute efficiency

MoE can improve quality for a given per-token compute budget because more model capacity is available to be selectively activated.

A dense model uses all parameters for every token. An MoE model can “specialize” experts on different patterns, domains, or linguistic structures.

This can produce better performance at a fixed active FLOP budget.

However, the efficiency depends on router quality:

- If the router chooses poor experts, the model wastes activation budget.
- If experts are too specialized, the model may lack generalization.
- If many tokens route to the same experts, some experts may be underused while others become bottlenecks.

### Trade-off
MoE can give higher quality per FLOP, but it adds routing overhead and requires careful tuning.

---

## 4. Inference latency and throughput

MoE inference is more complex than dense inference.

In a dense model, the computation graph is uniform: every token follows the same operations.

In an MoE model, different tokens select different experts. This creates dynamic, data-dependent computation.

Efficiency depends on:

- batch size
- expert load balance
- GPU cluster topology
- whether experts reside on same device
- ability to batch tokens by expert
- communication cost for all-to-all routing

At high batch size, MoE can be efficient because many tokens can be grouped and processed by each expert.

At very low batch size or latency-sensitive serving, the overhead of routing and expert scheduling can hurt performance.

### Trade-off
MoE often improves model quality at a target compute budget, but it can be less efficient for small-batch, low-latency inference due to routing and communication overhead.

---

## 5. Training stability and load balancing

Dense models are simpler to train because every token uses every layer in a regular way.

MoE introduces routing decisions, which can lead to problems:

- some experts get far more tokens than others
- certain experts may become “dead” and rarely used
- training may collapse into a small subset of experts
- load-balancing losses become necessary

Common remedies include:

- auxiliary load-balancing losses
- expert capacity limits
- token dropping or expert capacity constraints
- improved router designs
- careful initialization and scaling

These techniques add complexity and can affect model quality if poorly tuned.

### Trade-off
MoE enables sparse expert utilization, but at the cost of training stability and implementation complexity.

---

## 6. Scaling behavior

MoE is attractive for large-scale pretraining because it decouples model capacity from active compute.

A dense model must increase active FLOPs for every token if you want more parameters.

An MoE model can increase total capacity by adding experts while keeping top-\(k\) fixed. This can improve model quality while holding per-token compute roughly constant.

This is one reason MoE models have been used in frontier-scale research.

However, the scaling gains are not free:

- total storage increases
- optimizer states increase
- expert parallelism may be required
- routing may become harder as the number of experts grows
- diminishing returns can appear if experts are too redundant

### Trade-off
MoE provides a more flexible scaling law between memory, compute, and capacity, but it is harder to optimize at large scale.

---

## 7. Hardware utilization

Dense transformers are highly regular: matrix multiplications are uniform, memory access is predictable, and GPU utilization is straightforward.

MoE layers introduce sparsity and dynamic routing. This can lead to:

- irregular memory access patterns
- lower arithmetic intensity per expert
- underutilized GPUs if expert batching is inefficient
- increased communication in distributed settings

Modern MoE implementations can achieve good GPU utilization, but they often require specialized kernels, batching, and placement strategies.

### Trade-off
Dense models are hardware-friendly. MoE models can be more efficient in terms of model capacity per FLOP, but can be less efficient in terms of raw hardware utilization unless carefully engineered.

---

# Summary comparison

| Aspect | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Expert usage | All parameters used for each token | Only selected experts used per token |
| Total parameters | All parameters are active | Can be much larger than active parameters |
| Active FLOPs | Directly tied to model size | Can be controlled via top-\(k\) routing |
| Memory footprint | Lower for same total capacity | Higher because all experts must be stored |
| Inference simplicity | Simple and predictable | More complex due to routing |
| Training | Simpler, more stable | Requires load balancing, expert scheduling |
| Scaling | Linear increase in compute with size | Better capacity/compute separation |
| Main efficiency win | Regularity, stability, easy deployment | Higher capacity for similar per-token compute |
| Main efficiency risk | Compute grows with model size | Memory, routing, and load-balancing overhead |

---

# Bottom line

A **dense transformer** is simpler and more predictable: every token uses the full model, so scaling the model directly increases memory and compute in a regular way.

A **mixture-of-experts** model trades simplicity for sparsity: it stores many experts but activates only a few per token. This can improve model quality for a given active compute budget, but it introduces additional costs in memory, training complexity, load balancing, routing overhead, and inference scheduling.

In short:

- Use dense models when you want straightforward scaling, stable training, and easy serving.
- Use MoE when you want to increase model capacity without proportionally increasing per-token compute, and you can handle the added engineering complexity.
