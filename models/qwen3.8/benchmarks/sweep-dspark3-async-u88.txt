Mixture-of-experts (MoE) models are a way to increase a transformer’s total capacity without increasing the compute spent on every token as much as a dense model would. The core trade-off is: **MoE can give “more model” for a given per-token compute budget, but it introduces extra memory, routing, load-balancing, and communication costs.**

## 1. Dense transformer

In a standard dense transformer, every token passes through every layer’s full feed-forward network:

- Token input → attention → full FFN → next layer
- Each FFN is always active.
- Compute per token is roughly proportional to total parameters.

### Efficiency characteristics

**Compute:**  
Dense models have predictable compute. If you double the model width or depth, you roughly double the FLOPs per token.

**Memory:**  
You store all parameters, but you also use all parameters. There is less “unused weight” overhead.

**Serving behavior:**  
Inference cost scales straightforwardly with model size. Larger dense models are slower and more expensive per token.

**Training behavior:**  
Simpler optimization. No router, no expert load-balancing loss, no all-to-all communication across experts.

## 2. Mixture-of-experts transformer

An MoE model replaces one or more dense FFN layers with many smaller “expert” FFNs. For each token, a router selects the top-k experts, usually k = 1 or 2.

For example:

- 8 experts, top-2 routing
- 6B total parameters
- Each token activates ~1.5B parameters

So the model can have much higher total capacity than a fully active 1.5B dense model.

### Efficiency characteristics

**Compute:**  
Only a subset of experts is activated per token. For a given number of active parameters, MoE can often match or beat a dense model with larger total parameters.

**Memory:**  
All experts must be stored, even if only a few are used per token. This can increase GPU/TPU memory requirements and memory bandwidth pressure.

**Routing overhead:**  
There is a router, gating network, and possible token-to-expert dispatching. This is usually small relative to the experts, but not zero.

**Load balancing:**  
If many tokens route to the same expert, some experts become bottlenecks while others are underused. MoE training often uses auxiliary load-balancing losses or capacity constraints.

## Key efficiency trade-offs

| Aspect | Dense Transformer | Mixture-of-Experts | Trade-off |
|---|---|---|---|
| Total parameters | All parameters active | Many parameters, only subset active | MoE can have larger capacity at similar active compute |
| Compute per token | Scales with total parameters | Scales with active parameters | MoE can be more compute-efficient at inference |
| Memory footprint | Lower: only active parameters exist | Higher: all experts must be stored | MoE may require more accelerator memory |
| Memory bandwidth | Lower pressure: dense matmuls | Higher pressure: multiple expert FFNs may be loaded | MoE can be bandwidth-bound, especially at low batch sizes |
| Predictability | Very predictable FLOPs and latency | Latency can vary with routing and batch composition | Dense is easier to provision; MoE has more variance |
| Training complexity | Simpler | Requires router, load balancing, capacity handling | MoE can be harder to train stably |
| Communication cost | Local layer compute | Requires token dispatch to experts; often all-to-all in distributed serving | MoE can become communication-heavy in multi-GPU inference |
| Scalability | Increasing size increases compute and cost | Can increase capacity more cheaply than dense | MoE often better for scaling capacity at fixed compute budget |
| Quality | Good, but limited by active compute | Can outperform dense at same active FLOPs due to specialization | MoE often has a quality advantage, but not always monotonic |

## Where MoE wins

MoE is attractive when you want a large model with lower inference compute than a dense model of the same total size.

Example:  
An MoE model with 8 experts, each ~7B parameters, and top-2 routing may have:

- ~46B total parameters
- ~13B active parameters per token

It can behave more like a 13B dense model in compute, while having the capacity of a much larger model.

This is useful for:

- High-throughput inference
- Low-cost large-model serving
- Scaling quality without scaling active FLOPs linearly
- Specializing experts on different token types or subdomains

## Where dense wins

Dense models are often better when:

- You need predictable latency
- You have limited memory but can tolerate higher compute
- You want simpler training and inference stacks
- You are running at small batch sizes where MoE expert utilization may be poor
- You want fewer engineering complications

## Important nuance: active parameters vs total parameters

MoE models usually report two numbers:

- **Total parameters:** all experts combined.
- **Active parameters:** parameters actually used per token.

For example:

- Dense 13B model: 13B total, 13B active.
- MoE 46B total, 13B active: larger capacity, but similar per-token compute to a 13B dense model.

The efficiency question is not just “how many total parameters?” but:

> How much active compute do I spend per token, and what quality do I get for that compute?

## Practical takeaways

- **MoE trades storage and routing complexity for lower active compute.**
- **Dense models trade higher compute for simplicity and predictability.**
- MoE can be more efficient at inference if expert utilization is high and memory bandwidth is sufficient.
- MoE can be less efficient if experts are not balanced, if batch sizes are small, or if serving hardware cannot hold all experts in fast memory.
- For training, MoE offers a way to scale model capacity more cheaply than dense scaling, but it requires more sophisticated systems and optimization.
