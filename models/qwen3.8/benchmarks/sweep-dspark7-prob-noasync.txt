Mixture-of-Experts (MoE) and dense transformer architectures differ mainly in how they allocate and activate model capacity.

## Core architectural difference

### Dense transformer
In a standard dense transformer, every token in a layer passes through the same feed-forward network or attention-related submodules.

For each token, all parameters in the relevant layer are used.

If the model has \(P\) parameters, then approximately all \(P\) parameters contribute to each forward pass, at least in the sense that each token updates/reads the full dense weights for its layer.

### Mixture-of-Experts
In an MoE layer, instead of one dense feed-forward block, there are multiple expert networks, often small feed-forward blocks. A router selects the top-\(k\) experts for each token.

For example:

- 8 experts total
- each token uses 2 experts

Then the model has much larger total parameter count, but each token only activates a fraction of those parameters.

So MoE separates:

- **Total model size**: number of stored weights
- **Active compute per token**: number of weights actually used for a given token

---

# Key efficiency trade-offs

## 1. Parameter count vs. active compute

A dense model’s parameter count is roughly equal to the number of parameters used per token.

An MoE model can have:

- many more total parameters,
- but fewer or comparable active parameters per token.

Example:

| Architecture | Total experts | Experts used per token | Relative active compute |
|---|---:|---:|---:|
| Dense FFN | 1 | 1 | baseline |
| MoE with 8 experts, top-2 | 8 | 2 | higher than dense if experts are small |
| MoE with 64 experts, top-2 | 64 | 2 | active compute controlled, total capacity much larger |

This allows MoE models to store more knowledge or capability without proportionally increasing per-token FLOPs.

### Trade-off
You can scale capacity more efficiently than a dense model, but the benefits depend on how you measure efficiency:

- **FLOPs per token**: can be controlled
- **memory footprint**: grows with total expert count
- **training cost**: grows with number of expert parameters that receive gradients
- **inference cost**: can be low in FLOPs but high in memory bandwidth or expert scheduling complexity

---

## 2. Memory requirements

MoE models have a larger total parameter count because all experts must be stored, even though only some are used per token.

This affects:

- model checkpoint size
- GPU/TPU memory during training
- serving memory
- optimizer state memory

For dense models, memory scales directly with the active compute per token.

For MoE models, memory can scale with total expert count.

### Example
Suppose each expert is small.

Dense model:
- 1 expert-equivalent per token
- 1 set of parameters

MoE model:
- 32 experts
- only 2 used per token

The MoE model may have 32× the expert parameters, but each token only uses 2. It can therefore be much larger in total size while maintaining a similar per-token active FLOP budget.

### Trade-off
MoE gives more capacity for the same active compute, but requires more memory to store all experts.

---

## 3. Inference efficiency: FLOPs vs. bandwidth

MoE can be compute-efficient in FLOPs because only a subset of experts is activated per token.

However, inference is not only about FLOPs. It is also about:

- memory bandwidth
- expert scheduling
- batch routing
- cache behavior
- expert parallelism across accelerators

A MoE layer may require:

- routing computation
- token dispatch to experts
- expert computation on selected experts
- token recombination

This can introduce overhead that dense models do not have.

### Dense inference
- simpler
- more regular memory access
- easier to optimize with standard matrix multiplications
- often good utilization on GPUs

### MoE inference
- more complex
- less uniform across tokens
- potentially more communication overhead in multi-device settings
- can be efficient if experts are large enough and scheduling is optimized

### Trade-off
MoE may be better for scaling capacity at a fixed active compute budget, but it can be harder to make inference fast and efficient in practice.

---

## 4. Training complexity

Dense transformers are easier to train because every token affects every parameter in a layer.

MoE introduces routing, which creates additional challenges:

- load balancing across experts
- preventing dead experts
- preventing router collapse
- managing expert capacity
- handling routing instability
- optimizing multiple expert networks simultaneously

Common MoE techniques include:

- top-\(k\) routing
- expert capacity limits
- load-balancing auxiliary losses
- router z-losses
- expert parallelism
- token drop or overflow handling

### Trade-off
MoE can scale capacity more efficiently, but training is more fragile and requires more careful system design.

---

## 5. Expert utilization and routing quality

In dense models, there is no routing decision: every token uses the same sublayer.

In MoE models, quality depends on the router learning to send tokens to useful experts.

Problems include:

- some experts become overused
- some experts become underused
- certain token types are routed to the same experts
- rare tokens may not get enough expert capacity
- routing can become unstable during training

Good MoE training requires balancing:

- expert usage
- token capacity
- router confidence
- expert specialization

### Trade-off
MoE gains from specialization, but performance is sensitive to routing behavior.

---

## 6. Scaling laws

Dense models scale by increasing:

- layer count
- hidden size
- attention heads
- FFN width

MoE models scale by increasing:

- number of experts
- expert size
- number of experts selected per token
- router capacity
- expert capacity

MoE can often improve quality at lower active FLOPs than a dense model of the same active compute budget.

However, the gains are not free. They come with:

- larger model size
- higher training complexity
- more inference engineering effort
- more memory

### Trade-off
MoE can offer better quality for a fixed active compute budget, but total cost may be higher.

---

## 7. Batch-level efficiency

MoE efficiency depends heavily on batch composition.

If many tokens in a batch need the same experts, the system can compute those experts more efficiently.

If tokens are spread across many experts, scheduling becomes more expensive.

In other words:

- MoE benefits from expert reuse within a batch
- MoE can lose efficiency if tokens are routed too uniformly or too unevenly

Dense models have more predictable batch behavior because all tokens use the same weights.

### Trade-off
MoE can be more efficient when batch routing aligns well, but it is more sensitive to token distribution.

---

## 8. Model serving and hardware mapping

Dense models map cleanly onto standard GPU matrix operations.

MoE models require:

- expert placement across devices
- all-to-all or communication steps in some parallel schemes
- dynamic routing
- memory management for multiple experts

This can make MoE serving more complex, especially at large scale.

However, if the active compute per token is small, MoE can be attractive for serving because you get a larger effective model at lower per-token FLOPs.

### Trade-off
MoE can reduce active compute cost, but it increases serving complexity.

---

# Summary table

| Aspect | Dense transformer | Mixture-of-Experts |
|---|---|---|
| Parameters per token | All dense parameters active | Only top-\(k\) expert parameters active |
| Total model size | Tied to active compute | Can be much larger than active compute |
| Inference FLOPs | Scales with parameter count | Can be lower than total parameter count |
| Inference memory | Lower for equivalent active FLOPs | Higher because all experts are stored |
| Training | Simpler and more stable | More complex due to routing |
| Routing | None | Required |
| Load balancing | Not an issue | Major issue |
| GPU utilization | More predictable | More irregular |
| Communication | Usually lower | Can be higher in expert-parallel settings |
| Quality scaling | Requires more active compute | Can gain capacity by adding experts |
| Serving complexity | Simpler | More complex |

---

# High-level intuition

A dense transformer spends its compute uniformly: every token uses the full model.

A MoE transformer spends its compute selectively: it stores many specialized experts but activates only a few per token.

This makes MoE attractive when you want:

- a larger model
- lower active compute per token
- more model capacity at a fixed inference FLOP budget

But MoE introduces trade-offs:

- larger memory footprint
- more complex training
- routing instability
- harder inference optimization
- potential communication overhead

So the main efficiency trade-off is:

> **Dense models are simpler and more predictable; MoE models can achieve more capacity at lower active compute, but at the cost of higher total memory, training complexity, and serving complexity.**
