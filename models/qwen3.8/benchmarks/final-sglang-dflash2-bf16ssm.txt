At a high level:

- **Dense transformer**: every token is processed by the same full set of parameters in each layer. All parameters are active on every forward pass.
- **Mixture-of-Experts (MoE) transformer**: parts of the network—usually the feed-forward sublayers—are split into many “expert” modules, and a router selects only a small subset of experts for each token.

The main difference is that MoE decouples **total parameter count** from **parameters actually computed per token**.

---

## 1. Parameter count vs. active compute

In a dense transformer, if a model has \(P\) parameters, then roughly \(P\) parameters are active for each token. Compute cost scales directly with total model size.

In an MoE model:

\[
\text{total parameters} = P_{\text{total}}
\]

but only:

\[
P_{\text{active}} \ll P_{\text{total}}
\]

are used per token.

For example, an MoE layer may have 64 experts but activate only 2 per token. The model can therefore be much larger in total capacity while keeping per-token computation relatively low.

### Efficiency implication

MoE can increase model capacity without increasing per-token FLOPs proportionally. This is especially useful during pretraining, where you may want a very large model but a bounded compute budget.

---

## 2. Training efficiency

Dense transformers are usually easier to train efficiently:

- Large dense matrix multiplications
- High GPU utilization
- Simple, stable training pipeline
- Predictable compute cost

MoE introduces overhead:

- Token routing
- Expert dispatch and combine
- Load-balancing across experts
- Possible communication between devices if experts are parallelized
- More complex optimizer/memory management

However, MoE can be more **capacity-efficient**: for the same amount of training compute, it may store and use more parameters than a dense model.

### Efficiency implication

Dense models are often more hardware-efficient per FLOP.  
MoE models can achieve better quality at a given compute budget, but with more system and training complexity.

---

## 3. Inference memory footprint

A dense model needs its full weight set in memory, but every token uses all of it.

An MoE model must typically keep **all experts resident in memory or fast storage**, even though only a few are used per token.

So:

- Dense: memory footprint is lower for a given active compute.
- MoE: memory footprint can be much larger because unused experts still consume memory.

### Efficiency implication

MoE is attractive when you can afford extra memory but want lower per-token compute. It becomes harder if model weights must fit on a constrained device or if experts are offloaded to disk.

---

## 4. Inference compute and memory bandwidth

During inference, cost is often limited by:

- Number of parameters touched per token
- Memory bandwidth
- Batch size
- GPU utilization

For a dense model, every token loads the same FFN weights.

For MoE, each token loads only the weights of its selected experts. If \(k\) experts are selected out of \(E\), the FFN compute can be much lower than a dense layer of the same total size.

But there are trade-offs:

### Small batch inference

MoE can be inefficient because:

- Experts receive fewer tokens
- Matrix multiplications become smaller
- GPU utilization drops
- Routing/dispatch overhead matters more

### Large batch inference

MoE can be more efficient because:

- Many tokens can be routed to the same experts
- Experts can process tokens in large batches
- Total compute per token can be lower than a comparable dense model

### Efficiency implication

MoE inference is often most attractive for **high-throughput, large-batch serving**, but less attractive for **low-latency, small-batch** workloads.

---

## 5. Hardware and communication overhead

Dense transformers map very well to standard hardware:

- Large GEMMs
- Regular memory access
- Predictable computation graph

MoE introduces irregular computation:

- Different tokens use different experts
- Experts may have uneven token loads
- Expert parallelism often requires all-to-all communication

In a large training cluster with high-bandwidth interconnects, this may be manageable. On constrained hardware, it can be expensive.

### Efficiency implication

Dense models usually have better hardware efficiency and lower engineering overhead.  
MoE models can have lower per-token compute but higher system complexity.

---

## 6. Training stability and routing

MoE models require careful routing design. Without proper load balancing, the model may collapse into using only a few experts and ignoring the rest.

Common MoE overheads include:

- Auxiliary load-balancing losses
- Router training instability
- Expert capacity constraints
- Token dropping or dropping overflow tokens
- Sensitive hyperparameters

Dense transformers do not have these issues.

### Efficiency implication

MoE requires more tuning to get reliable scaling.  
Dense models are usually more robust and easier to scale.

---

## 7. Quality vs. efficiency trade-off

A common way to compare them is:

| Model type | Total params | Active params per token | Quality at fixed compute | Simplicity |
|---|---:|---:|---:|---|
| Dense | \(P\) | \(P\) | Baseline | High |
| MoE | \(P_{\text{total}} \gg P_{\text{active}}\) | \(P_{\text{active}}\) | Often better at same FLOPs | Lower |

MoE often behaves like a “larger model” in terms of capacity, while behaving like a “smaller model” in terms of per-token compute.

That is the core efficiency trade-off:

> MoE trades memory, routing complexity, and irregular computation for greater model capacity at lower per-token compute.

---

## Short version

**Dense transformers** use every parameter for every token. They are simpler, more hardware-friendly, and have predictable compute cost, but scaling up parameters increases both memory and compute.

**Mixture-of-Experts transformers** use many parameters in total but activate only a few per token. They can provide more capacity and often better quality for a given compute budget, but they require more memory, introduce routing overhead, suffer from load imbalance, and are less efficient in some inference regimes—especially low-batch or latency-sensitive settings.
