A **dense transformer** processes every token through the same full set of parameters at every layer. A **mixture-of-experts (MoE)** transformer keeps the same overall shape—attention, feed-forward network, normalization, etc.—but replaces some or all of the feed-forward blocks with a set of “expert” networks and a router that chooses which experts process each token.

The core efficiency difference is:

- **Dense models:** every token uses all parameters in the model.
- **MoE models:** each token only uses a small subset of the parameters, typically `top-k` experts.

That makes MoE models a way to increase total model capacity without increasing per-token computation proportionally.

---

## 1. Dense transformer architecture

In a standard dense transformer:

1. A token embedding is produced.
2. The token passes through transformer blocks.
3. Each block contains:
   - Multi-head self-attention
   - A position-wise feed-forward network
   - Layer normalization
4. Every token goes through the full attention module and full feed-forward network at every layer.

If the model has `P` parameters, then for every token, roughly all `P` parameters are used.

So the per-token compute is directly tied to total model size.

### Efficiency profile

**Pros**

- Simple architecture.
- Predictable compute and memory behavior.
- Easier to train, serve, and optimize.
- No routing complexity.
- Well-understood training dynamics.

**Cons**

- To increase model capacity, you must increase the number of active parameters.
- Increasing parameters usually increases FLOPs, memory bandwidth, and serving latency roughly in proportion.
- There is no built-in mechanism for “sparsity” or conditional computation.

In short: **dense models scale capacity by doing more work on every token.**

---

## 2. Mixture-of-experts architecture

In a typical MoE transformer:

1. The attention layers are usually still dense.
2. Some or all feed-forward layers are replaced with a set of experts.
3. A router/gating network looks at the token’s hidden state and selects the top-`k` experts.
4. The token is sent to those selected experts.
5. The expert outputs are combined, usually by a weighted sum.

For example, a layer may contain 64 experts, but each token only activates 2 of them.

### Active vs. total parameters

This distinction is central.

Suppose a model has:

- `N` experts per layer.
- Each expert has size `E`.
- The router selects `k` experts per token.
- All other components have parameter count `P_base`.

Then:

\[
\text{Total expert parameters} \approx N \cdot E
\]

\[
\text{Active expert parameters per token} \approx k \cdot E
\]

So:

- **Total model size** grows with `N`.
- **Per-token compute** grows with `k`, not `N`.

This is the main efficiency advantage of MoE.

### Efficiency profile

**Pros**

- Can scale total parameter count while keeping per-token active compute relatively fixed.
- Often improves quality at a given active FLOP budget.
- Can specialize experts to different domains or token types.
- Useful for large models where full dense scaling is too expensive.

**Cons**

- Total model memory is larger than active compute suggests.
- Training and serving are more complex.
- Expert load imbalance can waste capacity.
- Routing adds communication and memory overhead.
- Serving systems must handle dynamic, token-dependent compute.

In short: **MoE models scale capacity by adding more conditional parameters, but only use a subset per token.**

# 3. Key differences

| Aspect | Dense Transformer | Mixture-of-Experts |
|---|---:|---:|
| Parameters used per token | All parameters | Only selected experts |
| Total model size vs. active compute | Directly linked | Can be decoupled |
| Per-token FLOPs | Scales with total params | Scales with active expert params |
| Memory footprint | Smaller for same active compute | Larger because all experts must be stored |
| Training complexity | Simpler | More complex due to routing and load balancing |
| Serving complexity | Easier | Harder due to dynamic routing |
| Latency predictability | Highly predictable | Can vary with routing/batching |
| Capacity scaling | Increase width/depth | Add experts while controlling active FLOPs |
| Risk of underutilization | Low | Experts can be underused or overloaded |
| Communication overhead | Local tensor operations | Extra all-to-all or expert-parallel communication |

---

# 4. Compute efficiency trade-off

The most important trade-off is between **total parameters** and **active parameters**.

## Dense model

If you make a dense model bigger, you increase:

- Parameters
- FLOPs
- Memory bandwidth
- Serving cost

These usually grow together.

Example:

- Dense model A: 7B parameters, active 7B
- Dense model B: 13B parameters, active 13B

Larger model B means higher compute.

## MoE model

An MoE model can have a large total parameter count but only a small active fraction per token.

Example:

- Total parameters: 20B
- Active parameters per token: 2B

This can give much of the quality benefit of a larger model while using closer to 2B of compute per token.

However, the model still has 20B parameters stored in memory.

So the trade-off is:

\[
\text{High capacity + lower active compute, but higher total memory}
\]

---

# 5. Training efficiency trade-offs

## Active FLOPs

MoE can reduce active FLOPs relative to a dense model with the same total parameter count.

If you compare two models:

- Dense model: 10B total, 10B active
- MoE model: 20B total, 4B active

The MoE model has more total capacity but lower per-token compute.

This can be attractive if the goal is to scale model capacity without proportionally increasing training cost.

## Total memory and optimizer state

But MoE models still require storing all experts, gradients, and optimizer states.

Training memory often scales with **total parameter count**, not active parameter count.

So an MoE model may have:

- Lower active compute
- Higher memory usage
- Higher storage requirements
- More complex parallelism

In practice, MoE models often need:

- Expert parallelism
- Tensor parallelism
- Pipeline parallelism
- Communication optimization
- Careful batch sizing

This can offset some of the FLOP savings.

## Load balancing

A major training issue is expert load imbalance.

If many tokens route to the same experts and others are unused, the model wastes capacity.

MoE training usually uses:

- Auxiliary load-balancing losses
- Expert capacity limits
- Token dropping or expert capacity management
- Routers with smoother gate distributions

These add training complexity and can affect model quality.

## Router stability

The router is a dynamic component. If the router becomes unstable:

- Some experts may dominate.
- Some experts may become unused.
- Training can diverge or underperform.
- Expert utilization may become uneven.

This is a major practical difference from dense transformers, where every parameter participates every token.

---

# 6. Inference efficiency trade-offs

## Per-token compute

At inference time, MoE can be attractive because only a few experts are activated per token.

If serving cost is dominated by active compute and the experts fit in memory, MoE can give:

- Lower FLOPs per token
- Lower latency than a much larger dense model
- Higher capacity than a similarly active dense model

But this is not free.

## Memory footprint

MoE models are often larger on disk and in memory because all experts must be available.

For example:

- A dense 7B model may fit comfortably on one GPU.
- An MoE model with 50B total parameters but 7B active parameters may require more GPUs, expert parallelism, or offloading.

So MoE can be compute-efficient but memory-heavy.

## Batching effects

MoE serving is more sensitive to batching.

When many tokens are processed together, different tokens may use different experts. This can help reuse expert weights across a batch, improving utilization.

But if the batch is small or expert routing is highly skewed, you may see:

- Increased tail latency
- Poor expert cache utilization
- More memory access
- Need for expert offloading or scheduling

Dense models have more uniform memory access and simpler batching behavior.

## Expert parallelism

Large MoE models often distribute experts across multiple devices.

This introduces communication:

- Tokens must be routed to the correct experts.
- Results must be gathered back.
- All-to-all communication can become a bottleneck.

So MoE inference can improve compute efficiency but increase system complexity.

---

# 7. Quality vs. compute efficiency

A key motivation for MoE is that it often improves quality for a given active FLOP budget.

A dense model and an MoE model with the same active parameters are not necessarily equal in quality. The MoE model can have more total parameters, more conditional capacity, and more specialization.

So the efficiency trade-off is often:

| Goal | Better approach |
|---|---|
| Smallest model for a fixed FLOP budget | Dense may be simpler and sufficient |
| Higher quality at fixed active FLOPs | MoE can be better |
| Predictable latency and simple serving | Dense is usually better |
| Scaling capacity without proportional active compute | MoE is attractive |
| Low memory footprint | Dense is usually better |
| Large-scale training with conditional compute | MoE can be advantageous |

However, MoE does not automatically beat dense models. It usually works best at scale, with good routing, load balancing, and infrastructure support.

---

# 8. Memory, bandwidth, and storage trade-offs

Dense and MoE have different efficiency bottlenecks.

## Dense model bottleneck

For a dense model, if the model fits in memory, the main cost is:

- Number of active parameters
- FLOPs
- Memory bandwidth

If the model is too large, it may not fit on target hardware.

## MoE model bottleneck

For an MoE model, the main cost includes:

- Total expert storage
- Expert memory bandwidth
- Routing overhead
- Communication across devices
- Load imbalance
- Expert cache misses

Even if only 2 of 64 experts are used per token, the system often must store and potentially access all 64.

So MoE can be:

- **Compute-efficient:** fewer active FLOPs
- **Memory-heavy:** larger total parameter footprint

This is one of the central trade-offs.

---

# 9. Token routing and specialization

MoE models are input-dependent.

Different tokens may activate different experts. This can help the model represent:

- Different languages
- Different topics
- Different code styles
- Long-tail distributions
- Specialized behaviors

This conditional behavior can improve quality without increasing every token’s compute.

But it also introduces variability:

- Some tokens are “easier” and use fewer expert resources.
- Some tokens may hit overloaded experts.
- Some experts may become specialized in narrow domains.
- Some experts may rarely be used unless load balancing forces usage.

This makes MoE models more powerful but less uniform than dense models.

---

# 10. Where attention fits in

In most common MoE transformers, the MoE mechanism is applied to the **feed-forward layers**, not the attention layers.

So the structure is often:

- Dense attention
- MoE feed-forward layers
- Dense normalization and residual connections

This is important because attention cost can still be significant. MoE does not automatically make attention cheaper unless you use other techniques such as:

- Sparse attention
- Local attention
- Linear attention
- KV-cache optimizations

So an MoE model can reduce feed-forward compute while attention remains a major cost driver, especially for long sequences.

---

# 11. Practical efficiency summary

## Dense transformers

Best when:

- You need simplicity.
- You need predictable latency.
- The model must fit in limited memory.
- You do not need massive conditional capacity.
- You want straightforward training and serving.

Efficiency profile:

- Direct relationship between model size and compute.
- Lower memory footprint for a given active parameter count.
- Easier optimization.
- Less system complexity.

## MoE transformers

Best when:

- You want to scale capacity without proportionally increasing active FLOPs.
- You can tolerate larger total model memory.
- You have infrastructure for expert parallelism.
- You can tolerate more complex training and serving.
- You need high quality at a fixed active-compute budget.

Efficiency profile:

- Higher total capacity for fixed active compute.
- Lower active FLOPs than a comparable full-parameter dense model.
- Higher memory and storage cost.
- More communication and scheduling overhead.
- More sensitivity to load imbalance and routing quality.

---

# 12. Bottom line

The fundamental difference is:

> Dense transformers use all parameters for every token.  
> Mixture-of-experts transformers use a larger pool of parameters but only a small active subset per token.

The main efficiency trade-off is:

> MoE can increase model capacity while keeping per-token compute relatively constant, but it increases total model size, memory usage, training complexity, and serving complexity.

A dense model trades simplicity and memory efficiency against smaller total capacity.  
An MoE model trades memory and system complexity against higher capacity at a fixed active-compute budget.
