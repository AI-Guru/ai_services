A **dense transformer** uses all of its parameters for every token. A **mixture-of-experts (MoE) transformer** conditionally activates a subset of parameters—usually experts in the feed-forward layers—based on a routing decision. This decouples **model capacity** from **compute per token**, which is the central efficiency trade-off.

## Core architectural difference

### Dense transformer
- Every token passes through all layers and all weights.
- If the model has \(P\) parameters, the compute cost per token is roughly proportional to \(P\).
- Simple, predictable, and easier to train and serve.

Example:

\[
\text{FLOPs} \propto P_{\text{dense}}
\]

### Mixture-of-experts transformer
- The feed-forward layer is replaced by multiple “expert” subnetworks.
- A router selects the top-\(k\) experts for each token.
- Only those experts are computed for that token.

If there are \(E\) experts and each token uses \(k\), the expert compute is roughly:

\[
\text{active expert compute} \approx \frac{k}{E}
\]

of the compute needed if all experts were used.

Example: 8 experts, top-2:

\[
\frac{2}{8} = 25\%
\]

So the model can have many more total parameters than a dense model, while computing a smaller active parameter count per token.

## Efficiency trade-offs

| Dimension | Dense transformer | MoE transformer |
|---|---|---|
| Compute per token | Proportional to total parameters | Proportional to active parameters only |
| Memory | Lower total model memory | Higher total model memory because all experts are stored |
| Training complexity | Simpler, more stable | More complex due to routing, load balancing, capacity constraints |
| Inference latency | More predictable | Can have higher overhead from routing and expert communication |
| Throughput scaling | Scales straightforwardly | Can be excellent at high batch sizes if experts are well utilized |
| Data efficiency | Standard | Often better: more capacity without proportionally more compute |
| Hardware utilization | Highly regular, easy to optimize | Irregular, communication-heavy, harder to optimize |

## Compute efficiency

MoE can reduce compute cost per token while increasing model capacity.

For a MoE model with \(E\) experts and top-\(k\) routing, the active expert FLOPs are lower than a fully dense model of the same total expert size. This is useful when:

- compute is the bottleneck,
- you want larger effective capacity,
- you can afford higher memory and serving complexity.

However, the savings are not free:

- attention layers usually remain dense,
- the router adds overhead,
- only a subset of experts is active,
- expert load imbalance can reduce efficiency.

## Memory and communication trade-offs

MoE increases total parameter count, so it needs more memory to store:

- expert weights,
- router weights,
- optimizer states during training.

During training, the memory penalty can be large because every expert’s parameters need optimizer state, even though only some experts are active for a given token.

During inference, the model may be memory-bound. If all expert weights must be loaded, or if serving requires moving expert data across devices, the compute savings can be partially offset by:

- weight loading latency,
- cache misses,
- all-to-all communication in expert-parallel systems,
- lower GPU utilization due to irregular routing.

So MoE is often compute-efficient but not necessarily latency-efficient in small-batch or low-batch regimes.

## Training efficiency

Dense transformers are easier to train because every token updates the same set of weights. The computation graph is regular and stable.

MoE introduces several extra challenges:

- **Routing quality:** the router must make useful expert assignments.
- **Load balancing:** some experts may receive too many tokens, while others are underused.
- **Capacity limits:** in training, experts may have fixed token capacity, causing token dropping or overflow.
- **Instability:** auxiliary losses, router temperature, and expert specialization can affect convergence.
- **Communication:** expert parallelism requires moving tokens between devices, which can dominate training time.

These make MoE more difficult to scale, but when done well it can improve quality-per-FLOP.

## Inference and serving trade-offs

MoE often shines in **high-throughput serving**, where many tokens per batch keep experts busy. The system can amortize expert weight access and communication costs.

But for **low-latency, small-batch inference**, MoE can be less attractive because:

- only a few tokens may be routed through each expert,
- routing and communication overhead becomes significant,
- expert weight access can dominate,
- latency variance may be higher than a dense model.

A small dense model can sometimes be faster per request than a MoE model with the same active compute budget.

## Quality vs efficiency

MoE models often improve quality at a given active compute budget because they can store more knowledge across many experts while activating only a few per token. This makes them attractive for large language models where:

- capacity is limited by memory,
- compute per token is constrained,
- batch size is large enough to saturate experts.

But the benefits depend on design choices:

- top-1 routing is cheaper but less robust,
- top-2 routing is more expensive but often more stable,
- expert size matters: very small experts may be underpowered,
- load balancing can reduce specialization if too aggressive.

## Rule of thumb

- **Dense transformers** are better when you want simplicity, low latency, stable training, small models, or predictable serving.
- **MoE transformers** are better when you want more capacity without proportionally increasing per-token compute, and you can tolerate higher memory, communication, and system complexity.

In short: **MoE trades memory, communication, and engineering complexity for lower active compute and higher model capacity.** Dense transformers trade raw scalability for simplicity and predictable efficiency.
