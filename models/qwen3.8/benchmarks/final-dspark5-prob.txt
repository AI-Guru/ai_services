A **dense transformer** applies the same set of weights to every token. A **mixture-of-experts (MoE) transformer** replaces some feed-forward layers with multiple “expert” sub-networks and uses a router to select a small subset of experts per token.

## Core architectural difference

### Dense transformer
- Every token passes through all parameters in each layer.
- If the model has 10B parameters, roughly 10B parameters are used for every token.
- Computation is dense: every token pays the same compute cost.

### Mixture-of-experts
- A router chooses, for each token, a few experts, e.g. top-1 or top-2.
- Only the selected experts’ weights are used for that token.
- The model can have many more total parameters, but far fewer are active per token.

Example:

| Model type | Total parameters | Active parameters per token |
|---|---:|---:|
| Dense 10B | 10B | 10B |
| MoE 10B, top-2 | 10B | maybe 2B |

So MoE can increase model capacity while keeping per-token compute lower.

## Efficiency trade-offs

### 1. Compute efficiency
MoE models can achieve higher capability for a fixed amount of compute because they use a larger total parameter pool while activating only a fraction per token.

- **MoE advantage:** more capacity per FLOP.
- **Dense advantage:** compute cost is uniform and predictable.

In other words, MoE trades parameter size for lower active compute per token.

### 2. Memory and bandwidth
MoE models store many expert weights, even if only a few are used for each token.

- **MoE disadvantage:** large model memory footprint.
- In inference, the model must load expert weights from memory. If a batch of tokens activates many different experts, this can become memory-bandwidth-bound.

Dense models have a smaller memory footprint for the same active compute, but less total capacity.

### 3. Batch and throughput efficiency
MoE efficiency depends strongly on batch size and how experts are scheduled.

- With large batches, many tokens can share the same expert computations, improving throughput.
- With very small batches, the model may load many experts to process a few tokens, reducing efficiency.
- Inference systems must expert-parallelize or schedule work across devices, adding complexity.

Dense models are simpler to serve because every token uses the same layers.

### 4. Training complexity
MoE introduces routing and load-balancing challenges:

- Some experts may receive more tokens than others.
- Load-balancing losses and expert routing decisions are needed.
- Training can be less stable if experts underutilize or overfit.
- Communication overhead may increase in distributed training, especially with expert parallelism.

Dense transformers are generally easier to train, scale, and debug.

### 5. Communication overhead
In large-scale distributed training or inference:

- MoE often requires expert parallelism, where different experts are placed on different devices.
- Tokens or activations must be routed between compute nodes.
- This can add all-to-all communication costs.

Dense models primarily use tensor or data parallelism, which is simpler and often more predictable.

### 6. Accuracy-per-compute trade-off
MoE often provides better quality at a given active compute budget because it can store more knowledge in its inactive parameters.

For example, a MoE model may match or exceed a larger dense model while using less compute per token. But it may require:

- more total memory,
- more complex serving infrastructure,
- careful routing and load balancing.

## When MoE is more attractive
MoE is useful when:

- You want high model capacity under a fixed compute budget.
- You have enough memory or hardware to store many experts.
- Inference batches are large enough to amortize expert-loading and routing overhead.
- You need strong quality-per-FLOP scaling.

## When dense is more attractive
Dense is simpler and often better when:

- You need low serving latency or small-batch inference.
- You have limited memory for model weights.
- You want simpler training and deployment.
- Predictable, uniform compute is more important than maximum capacity.

## Bottom line
**Dense transformers** spend the same compute on every token and are simpler to train and serve. **MoE transformers** store more parameters but activate only a subset, giving higher capacity per active FLOP at the cost of extra memory, routing complexity, and communication overhead. The main efficiency trade-off is: **MoE trades model simplicity and memory footprint for better compute utilization and greater total capacity.**
