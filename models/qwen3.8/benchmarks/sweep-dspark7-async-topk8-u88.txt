Mixture-of-experts (MoE) transformers and dense transformers differ mainly in how they allocate model capacity across tokens.

## Core architectural difference

### Dense transformers
In a standard dense transformer:

- Every token passes through every expert layer.
- Each token is transformed by the same set of parameters.
- The model’s compute per token is fixed.

If an FFN layer has size `N`, every token performs the same `N` parameter interactions.

### Mixture-of-experts transformers
In an MoE transformer:

- The FFN layer is replaced by several specialized subnetworks called “experts.”
- A router/gate selects a subset of experts, usually top-k, for each token.
- Only the selected experts are used for that token.

So a model can have many more total parameters while each token only activates a smaller fraction of them.

Example:

- Dense model: 70B total parameters, 70B active parameters per token.
- MoE model: 230B total parameters, 30B active parameters per token.

The MoE model has larger capacity but lower per-token compute.

---

## Key efficiency trade-offs

### 1. Compute vs. parameter count

#### Dense
- Compute scales directly with total parameter count.
- More parameters generally means more FLOPs.
- Easier to reason about runtime cost: FLOPs are relatively constant across inputs.

#### MoE
- Total parameter count can be large.
- Active compute per token is much smaller because only a few experts are used.
- Allows large model capacity with lower training/inference FLOPs than a fully dense model of the same total size.

Trade-off:

- **MoE:** more capacity for less compute.
- **Dense:** less capacity unless you increase active parameters, which increases cost.

---

### 2. Memory and storage

MoE models usually have more total parameters than dense models of similar active compute.

That creates a memory trade-off.

#### Dense
- All parameters are used for every token.
- Memory footprint is straightforward and stable.
- Better GPU utilization if parameters fit and are well reused.

#### MoE
- Total parameter count is larger, so models often require more storage.
- During inference, many experts may need to be resident in memory or loaded on demand.
- Serving can become memory-bandwidth-bound, especially when different tokens use different experts.

Trade-off:

- **MoE:** cheaper compute, but higher memory/storage cost.
- **Dense:** more predictable memory behavior, but less efficient if you need large capacity.

---

### 3. Routing and scheduling overhead

MoE adds a gating mechanism. This creates additional costs that dense models do not have.

For each token, the model must:

- compute router logits,
- select top experts,
- route tokens to experts,
- combine expert outputs.

This introduces:

- extra computation for routing,
- communication overhead in distributed systems,
- dynamic scheduling complexity,
- load-balancing pressure across experts.

Trade-off:

- MoE can reduce main FFN compute, but routing may hurt latency or increase complexity.
- Dense architectures avoid this overhead.

---

### 4. Load balancing

A major practical issue with MoE is that some experts can become popular while others are underused.

If routing concentrates tokens on a few experts:

- those experts become bottlenecks,
- utilization becomes uneven,
- training can become unstable,
- inference throughput can suffer.

Dense models do not have this problem because all layers are used uniformly.

MoE systems often use load-balancing losses, expert capacity limits, or expert-parallel serving to mitigate this.

Trade-off:

- **MoE:** requires careful balancing for good hardware efficiency.
- **Dense:** simpler scheduling and more predictable utilization.

---

### 5. Training efficiency

MoE can be more parameter-efficient during training:

- Larger model capacity can be learned without proportionally increasing FLOPs.
- Smaller effective active model can converge faster for a given compute budget.
- Can improve scaling behavior compared with dense models of the same active size.

However, MoE training is more complex:

- expert load must be balanced,
- routing decisions affect optimization,
- expert updates are sparse,
- distributed training may require more communication.

Dense training is simpler:

- All parameters are updated regularly.
- Easier to parallelize and optimize.
- More stable but less capacity per FLOP.

Trade-off:

- **MoE:** potentially better quality for a given compute budget, but harder to train well.
- **Dense:** easier to train, but requires more compute for equivalent capacity.

---

### 6. Inference latency vs. throughput

MoE models often improve throughput in batched inference:

- More tokens can be processed per unit compute because fewer parameters are active per token.
- They can be attractive for large-scale serving.

But latency can be harder to optimize:

- Expert dispatch may increase tail latency.
- Different tokens use different experts.
- Memory movement may dominate for small batch sizes.

Dense models are usually more predictable:

- Similar latency behavior across inputs.
- Easier to optimize for single-stream or low-batch serving.

Trade-off:

- **MoE:** often better for high-throughput serving, but can have higher complexity and variable latency.
- **Dense:** more predictable latency, especially for single-request workloads.

---

### 7. Batch effects

MoE behavior depends strongly on batch size.

With small batches:

- fewer tokens are available to spread across experts,
- expert utilization can be poor,
- memory movement may dominate.

With large batches:

- more tokens can be routed to different experts,
- load balancing improves,
- compute efficiency can increase.

Dense models do not have this batch-size sensitivity in the same way.

Trade-off:

- **MoE:** can scale well with large batches but may be inefficient at small batch sizes.
- **Dense:** more consistent behavior across batch sizes.

---

## Summary table

| Aspect | Dense Transformer | Mixture-of-Experts Transformer |
|---|---|---|
| Parameter usage | All parameters active per token | Only a subset active per token |
| Compute per token | Higher for large models | Lower for same total size |
| Memory footprint | More compact | Larger due to many experts |
| Routing overhead | None | Nontrivial |
| Load balancing | Not needed | Critical |
| Training simplicity | Simpler | More complex |
| Serving predictability | High | More variable |
| Throughput efficiency | Good | Often better for large batches |
| Capacity per FLOP | Lower | Higher |

---

## Bottom line

Dense transformers are simpler and more predictable: every token uses every layer, so compute, memory, and latency are easier to estimate.

Mixture-of-experts transformers trade that simplicity for efficiency: they allow a model to store and learn a much larger parameter space while only spending compute on a smaller active subset. The result is often better capacity-per-FLOP, but at the cost of higher memory requirements, routing overhead, load-balancing complexity, and more challenging inference serving.
