Mixture-of-experts (MoE) and dense transformer architectures differ mainly in **which parameters are used to process each token**. That difference creates a different trade-off between **parameter count, compute cost, memory cost, and practical efficiency**.

## 1. Core architectural difference

### Dense transformer
In a standard dense transformer, every token passes through the same set of parameters at every layer.

For each token:

- The attention layer is fully applied.
- The feed-forward network is fully applied.
- All parameters in the model contribute to every forward pass.

So for a dense model:

\[
\text{active parameters} = \text{total parameters}
\]

Every token sees the full model.

---

### Mixture-of-experts transformer
A MoE model replaces part of the standard dense block, usually the feed-forward network, with a router plus multiple “expert” networks.

For each token:

- A lightweight router decides which experts are relevant.
- The token is sent to only a small subset of experts, often top-1 or top-k experts.
- Only the selected experts are activated.

So for a MoE model:

\[
\text{active parameters} \ll \text{total parameters}
\]

The model can have many more total parameters than a dense model, but each token only uses a small subset.

---

## 2. Main efficiency trade-off: parameters vs compute

The central idea of MoE is to **decouple total model size from per-token compute cost**.

For a dense model, increasing model size generally increases both:

- parameter count,
- FLOPs per token.

For a MoE model, you can increase:

- total parameter capacity,

while keeping:

- per-token active compute relatively fixed.

This creates a useful trade-off:

| Goal | Dense model | MoE model |
|---|---|---|
| Fixed active compute | Smaller total capacity | Larger total capacity, same FLOPs |
| Fixed total parameters | Higher per-token compute | Lower per-token compute |
| Scaling model size | Compute grows linearly | Compute can grow sublinearly |

In other words:

- A MoE model with 100B total parameters may use only 10B active parameters per token.
- A dense 10B model uses 10B active parameters per token.
- The MoE model may therefore have much more capacity while having similar per-token compute to the dense model.

---

## 3. Compute efficiency

### Dense transformers
Dense transformers have predictable compute:

- every token runs the same operations,
- layers have regular shapes,
- matrix multiplications are highly regular,
- hardware utilization is usually high.

This makes dense models easy to optimize and very efficient in practice.

### MoE models
MoE models can reduce active FLOPs because only some experts run per token.

For example, if a layer has 8 experts and uses top-2 routing, then only 2 out of 8 expert paths are active for each token.

This can give a compute advantage compared with a dense model of the same total size.

However, MoE introduces overhead:

- routing/gating computation,
- token-to-expert routing,
- load balancing,
- irregular expert activation,
- grouped matrix multiplications,
- communication between devices in distributed inference.

So MoE can be more compute-efficient in theory, but the practical speedup depends heavily on serving infrastructure.

---

## 4. Memory trade-off

This is one of the biggest practical differences.

### Dense model
Memory cost is mostly proportional to active parameters:

\[
\text{memory} \approx \text{total parameters}
\]

This is simple and predictable.

### MoE model
Memory cost is closer to total parameters:

\[
\text{memory} \approx \text{total parameters}
\]

Even though only a small fraction of experts is active per token, all experts still need to be stored somewhere.

So MoE models often have a much larger memory footprint than a dense model with the same active compute.

This creates a key trade-off:

- MoE: larger total parameter count, better capacity, but higher memory demand.
- Dense: smaller memory footprint, simpler storage, but less capacity for the same compute budget.

---

## 5. Training efficiency trade-offs

MoE models can be more efficient in terms of training FLOPs, but they are harder to train.

### Advantages
- You can scale capacity without increasing per-token FLOPs proportionally.
- For a fixed training compute budget, a MoE model may reach better performance than a smaller dense model.
- Useful when compute is the bottleneck but memory can be increased.

### Costs
- Training MoE models is less stable.
- You need load-balancing losses to avoid some experts being underused.
- You need careful routing design.
- Optimizer state memory is much larger because there are more total parameters.
- Distributed training requires extra communication, especially with expert parallelism.

So MoE can be more compute-efficient, but it is often less “efficient” in terms of engineering simplicity, stability, and serving complexity.

---

## 6. Inference efficiency

MoE inference has a complex trade-off.

### If experts fit in memory
A MoE model can be faster than a dense model of the same total size because only a subset of experts is activated.

For example, a MoE model with 100B total parameters but 10B active parameters may have inference FLOPs closer to a 10B dense model.

### If experts do not fit in memory
MoE can become inefficient because:

- experts may need to be fetched from slower memory,
- routing may cause cache misses,
- batch sizes may be too small to keep experts efficiently loaded,
- all-to-all communication can dominate.

Dense inference is more predictable:

- the same weights are reused for every token,
- memory access patterns are regular,
- serving stacks are better optimized.

So MoE can be very fast at large batch sizes or when expert parallelism is well matched to the hardware, but dense models are often easier to serve.

---

## 7. Batch size and hardware utilization

MoE and dense models behave differently across batch sizes.

### Low batch inference
At small batch sizes, inference is often memory-bound.

MoE can be disadvantaged because:

- the system may need to load multiple experts,
- only a few tokens are routed to each expert,
- hardware utilization can drop.

Dense models tend to perform more consistently at low batch size because the same weights are reused for all tokens.

### High batch throughput
At high batch sizes, MoE can shine if:

- experts are distributed across devices,
- tokens are balanced across experts,
- communication overhead is manageable.

In that regime, MoE can provide high throughput while maintaining a large total model capacity.

---

## 8. Quality and scaling trade-offs

MoE models often scale better in terms of model capacity, but the gain is not free.

### Potential benefit
For the same active compute, MoE can have more total parameters, which may improve:

- knowledge capacity,
- task specialization,
- generalization,
- performance on heterogeneous data.

### Potential downside
More parameters do not automatically mean better performance if:

- experts are underused,
- routing is poorly balanced,
- the model has not seen enough data to exploit the extra capacity,
- training stability is poor.

So MoE can be more “parameter-capacity efficient,” but it is not always automatically better quality for the same compute and data budget.

---

## 9. Practical engineering trade-off

Dense models are generally:

- easier to train,
- easier to serve,
- more stable,
- easier to debug,
- more hardware-friendly.

MoE models are:

- more capacity-efficient,
- potentially more compute-efficient,
- more scalable in total size,
- but harder to train and serve efficiently.

---

## 10. Summary table

| Dimension | Dense transformer | Mixture-of-experts transformer |
|---|---|---|
| Parameters used per token | All parameters | Only routed expert subset |
| Total parameter capacity | Directly tied to compute | Can be much larger than active compute |
| FLOPs per token | Scales with total size | Can be lower than total size |
| Memory footprint | Lower and simpler | Higher because all experts are stored |
| Compute predictability | High | Lower due to routing and load imbalance |
| Training stability | Generally easier | Harder; needs load balancing and careful tuning |
| Inference latency | More predictable | Can be fast at scale, but variable |
| Batch-size behavior | Stable at low batch | May struggle at low batch; can win at high throughput |
| Best use case | Simpler, predictable, efficient serving | Large capacity with constrained active compute |

---

## Bottom line

The main difference is:

- **Dense transformers use all their parameters for every token**, so parameter count and compute cost scale together.
- **MoE transformers use only a subset of parameters for each token**, so they can have much larger total capacity without a proportional increase in per-token compute.

The key efficiency trade-off is therefore:

\[
\text{MoE: more capacity and potentially lower active compute, but higher memory and serving complexity}
\]

\[
\text{Dense: simpler, more predictable, and easier to serve, but less capacity for the same compute budget}
\]
