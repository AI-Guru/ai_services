Mixture-of-Experts (MoE) and dense transformers differ mainly in how much of the model is used to process each token.

### Core architectural difference

**Dense transformer:**
- Every token passes through all parameters in each layer.
- For a transformer layer with an MLP block, each token uses the same full feed-forward network.
- Compute cost is proportional to total parameter count per token.

**Mixture-of-Experts:**
- Replaces some or all dense MLP blocks with a router and multiple expert subnetworks.
- For each token, the router selects a small subset of experts, usually top-1 or top-2.
- The model can have many more total parameters, but only a fraction are activated per token.

Example: an MoE layer with 8 experts and top-2 routing may have 8× the parameters of a single expert, but only uses 2 of them per token.

---

### Efficiency trade-offs

#### 1. Compute efficiency

**Dense:**
- Uses all parameters for every token.
- Predictable FLOPs per token.
- Easier to optimize with standard dense matrix multiplication.

**MoE:**
- Uses fewer active parameters per token.
- Can provide higher model capacity without a proportional increase in per-token compute.
- For the same active compute budget, an MoE model can often encode more knowledge than a dense model.

Trade-off: MoE improves compute scalability, but only if routing is effective and experts are used well.

---

#### 2. Memory footprint

**Dense:**
- Model size is tied to active parameters.
- Simpler to fit on hardware; all parameters are used during inference.

**MoE:**
- Total parameter count is usually much larger than active parameter count.
- All experts must typically be stored in memory, even if only a few are active per token.
- This can require expert parallelism, sharding, offloading, or larger accelerators.

Trade-off: MoE trades lower per-token compute for higher memory requirements.

---

#### 3. Inference latency and bandwidth

**Dense:**
- Often efficient for low-latency, small-batch inference.
- Uses well-optimized dense kernels.
- Memory access patterns are regular.

**MoE:**
- Per-token compute can be lower, but latency can be hurt by:
  - Router overhead
  - Expert lookup
  - Non-uniform memory access
  - Fetching different experts for different tokens
  - All-to-all communication in distributed settings
- MoE shines more in high-throughput batch inference than in single-token latency-sensitive serving.

Trade-off: MoE can be cheaper per token, but not always faster per token.

---

#### 4. Training efficiency

**Dense:**
- Training is straightforward.
- All parameters are updated for each token.
- Optimizer state and memory requirements scale directly with total parameter count.

**MoE:**
- More total parameters means larger memory demand for gradients and optimizer states.
- Requires techniques such as:
  - Expert parallelism
  - Expert sharding
  - Load balancing losses
  - Expert dropout or capacity factors
  - Careful routing initialization
- Training stability can be harder to achieve.
- Poor load balancing can leave some experts undertrained or unused.

Trade-off: MoE can scale capacity efficiently, but it is harder to train and requires more infrastructure.

---

#### 5. Model capacity versus accuracy

**Dense:**
- Increasing capacity usually increases both parameter count and compute.
- Scaling is predictable but expensive.

**MoE:**
- Allows “sparse scaling”: more capacity without matching compute increase.
- Often improves data efficiency or benchmark performance at the same active FLOPs.
- However, gains depend on good routing, expert diversity, and balanced expert usage.

Trade-off: MoE can give better scaling, but only with careful design.

---

### Summary

| Dimension | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Active parameters per token | All | Subset |
| Total model size | Smaller | Larger |
| Compute per token | Higher | Lower, for same capacity |
| Memory footprint | Lower | Higher |
| Inference simplicity | Simpler | More complex |
| Latency behavior | Usually better for small batches | Better for high-throughput serving |
| Training complexity | Lower | Higher |
| Scaling behavior | Capacity and compute scale together | Capacity can scale faster than compute |

In short: **dense transformers are simpler and more predictable; MoE models trade memory, routing, and systems complexity for lower per-token compute and greater capacity scaling.**
