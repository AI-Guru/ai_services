Mixture-of-Experts (MoE) and dense transformers share the same basic transformer building blocks—attention, layer norm, feed-forward layers—but they differ in how the feed-forward component is activated for each token.

## Core architectural difference

### Dense transformer
In a dense transformer, every token passes through **all parameters** of each layer’s feed-forward network.

For a token in layer `i`, the model computes:

```text
FFN(x) = W2 * nonlinearity(W1 * x + b1) + b2
```

If the model has, say, 7B total parameters, then roughly all 7B parameters are used to process each token.

So the relationship is:

```text
Total parameters ≈ active parameters per token
```

### Mixture-of-Experts transformer
In an MoE transformer, the feed-forward layer is replaced by multiple smaller “expert” networks and a router.

For each token, the router selects a small subset of experts, usually `top-k` experts:

```text
FFN(x) = Σ w_e(x) * Expert_e(x)
```

where only `k` experts are active for that token, often `k = 1` or `k = 2`.

So an MoE model can have many total parameters but only a small fraction active per token.

Example:

```text
Total parameters: 45B
Active parameters per token: 13B
```

This means the model stores more knowledge, but each token does less compute than if all experts were used.

---

## Main efficiency trade-offs

| Dimension | Dense Transformer | Mixture-of-Experts |
|---|---|---|
| Active compute per token | All parameters are used | Only selected experts are used |
| Total parameter count | Smaller for a given active-compute budget | Can be much larger |
| Training FLOPs per token | Higher for large models | Lower if few experts are active |
| Memory footprint | Lower | Higher, because all experts are stored |
| Inference latency | More predictable | Can be higher due to routing, communication, expert scheduling |
| Implementation complexity | Simpler | More complex |
| Scaling behavior | Quality scales with total compute | Can trade capacity against compute |
| Deployment | Easier to deploy | More complex, often requires expert parallelism |
| Risk of inefficiency | Stable, well-understood | Load imbalance, expert underuse, capacity overflow |

---

## 1. Compute efficiency: MoE can do more with less FLOPs

Dense models have a fixed relationship between model size and compute cost. If you increase the model from 7B to 70B parameters, inference compute per token increases roughly proportionally.

MoE decouples this relationship.

A model can have:

```text
Large total parameters
Small active parameters
```

This allows a model to have a large “knowledge bank” while limiting per-token compute.

For example, an MoE model might have:

```text
Total parameters: 100B
Top-1 experts
Active parameters: 10B
```

In that case, the model stores 100B parameters, but each token only uses about 10B parameters. That can be much more efficient than a dense 100B model, which would activate roughly 100B parameters per token.

This is one of the biggest advantages of MoE: **capacity without proportional compute cost**.

---

## 2. Memory efficiency: MoE trades memory for compute

The catch is memory.

Even if only a few experts are active per token, the model still has to store all expert weights in memory, at least during inference and training.

So MoE models often have:

```text
Lower FLOPs per token
Higher memory per layer
```

This creates a tension:

- Dense: smaller memory, higher compute.
- MoE: larger memory, lower compute per token.

For inference, this matters because many systems are memory-bandwidth limited. An MoE model can be fast in raw FLOPs but slower in practice if it has to load large numbers of experts from memory or across devices.

So MoE is not simply “cheaper” in all senses. It shifts the bottleneck from compute to memory and system complexity.

---

## 3. Training efficiency: lower FLOPs, but more complexity

During training, MoE can reduce the amount of computation per token because each token only updates a few experts.

This can make large-scale training more compute-efficient. Instead of increasing dense model width, you can add experts and grow total capacity while keeping per-token FLOPs lower.

However, MoE introduces extra training challenges:

### Expert load balancing
If the router always chooses the same experts, some experts become overused while others are underused. That wastes capacity.

MoE training often uses auxiliary load-balancing losses to encourage tokens to be distributed evenly across experts.

### Capacity constraints
Each expert has a fixed number of tokens it can process per step. If too many tokens are routed to one expert, some tokens may be dropped or delayed. This introduces a trade-off between:

```text
Expert capacity
Load balance
Quality
```

### Router sensitivity
The router is a small component, but it strongly affects behavior. A bad router can cause:

- poor expert utilization,
- unstable training,
- mode collapse where a few experts dominate,
- degraded performance.

Dense models do not have this routing problem.

---

## 4. Inference efficiency: faster FLOPs, but system-dependent

For a single token, MoE can reduce active compute. But real inference speed depends on the serving system.

Advantages:

- fewer active parameters,
- potentially lower compute per token,
- can serve larger-capacity models at lower compute cost.

Disadvantages:

- all experts must be resident or fetchable,
- dynamic routing can cause memory access patterns,
- expert parallelism may require communication,
- batching and expert scheduling are harder,
- latency can be less predictable.

For example, on a single GPU, a dense model may be simpler and faster because all weights are used in a predictable way. An MoE model may require more sophisticated serving infrastructure to avoid memory bottlenecks.

---

## 5. Quality vs compute scaling

MoE models can often achieve better quality at a fixed active-compute budget.

Instead of:

```text
Dense: increase parameters → increase compute proportionally
```

MoE can do:

```text
MoE: increase total parameters → increase capacity, but keep active compute lower
```

This can be useful when:

- you want a large knowledge capacity,
- but you want to limit inference cost,
- or you are scaling a model where compute per token matters more than total memory.

However, MoE does not automatically beat a dense model. A dense model with the same total parameter count and enough compute may still be simpler and more robust. MoE is most useful when you want to scale capacity while controlling per-token compute.

---

## 6. Simplicity and stability

Dense transformers are easier to train, debug, scale, and deploy.

They have:

- no router,
- no expert load-balancing losses,
- no expert scheduling,
- no capacity overflow,
- simpler memory access patterns.

MoE adds complexity in:

- router design,
- expert routing,
- load balancing,
- expert parallelism,
- batching,
- memory management,
- expert activation,
- system integration.

For many production workloads, this extra complexity may not be worth it. Dense models are often preferred when:

- the model is small or medium-sized,
- memory is limited,
- deployment simplicity matters,
- training stability is critical,
- or the team lacks infrastructure for expert parallelism.

---

## 7. Where MoE tends to help most

MoE is especially useful when:

- you want a very large model but cannot afford dense compute,
- inference compute is more important than total parameter count,
- you can afford extra memory for expert weights,
- you have a serving system that can handle expert scheduling,
- you want to scale model capacity faster than compute.

MoE is less attractive when:

- memory is tight,
- the model must fit on a single device,
- low-latency inference is critical,
- deployment simplicity is essential,
- or the team lacks experience with distributed expert serving.

---

## Intuitive summary

A dense transformer is like a small team where every employee works on every task.

A MoE transformer is like a large organization where each task is routed to a few specialized experts. The organization has more total expertise, but each task uses fewer people.

The trade-off is:

```text
Dense:
  smaller memory
  higher compute per token
  simpler system

MoE:
  larger memory
  lower active compute per token
  more complex system
```

In short, MoE decouples **model capacity** from **per-token compute**, but pays for that flexibility with higher memory usage, routing complexity, and systems overhead. Dense models are simpler and more predictable, while MoE models can achieve better compute-to-capacity efficiency when the deployment environment supports them.
