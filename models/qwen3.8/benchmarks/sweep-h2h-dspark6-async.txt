Mixture-of-Experts (MoE) and dense transformer architectures both use the same basic transformer block—attention plus feed-forward networks—but they differ in how computation is allocated per token.

## Core difference

### Dense transformer

In a dense transformer, every token passes through **all** parameters in every layer, including every feed-forward block.

So if a model has 7B parameters, approximately all 7B parameters are used for every token.

### Mixture-of-Experts transformer

In an MoE model, one or more layers—usually the feed-forward layers—are replaced with multiple “experts.” Each token is routed to only a small subset of those experts, commonly top-1 or top-2.

For example:

- A model might have 8 experts in a given layer.
- Each token is routed to 2 experts.
- The model may have a large total parameter count, but only a fraction of the parameters are active per token.

So an MoE model can have, for example, 100B total parameters while activating only 10–20B parameters per token.

---

# Key efficiency trade-offs

## 1. Compute: MoE is cheaper per token

The biggest efficiency advantage of MoE is **compute efficiency**.

For a dense model, compute scales with:

> active parameters × tokens

For an MoE model, compute scales closer to:

> active parameters per token × tokens

Because only a subset of experts is activated, an MoE model can have a much larger total parameter count while still using less compute per token than an equivalently sized dense model.

This is why MoE models often achieve better quality than smaller dense models at the same inference compute budget.

Example intuition:

| Model type | Total parameters | Active parameters per token | Relative compute |
|---|---:|---:|---:|
| Dense 7B | 7B | ~7B | High |
| MoE 48B total / 8B active | 48B | ~8B | Low |

The MoE model stores many more parameters, but it only uses a subset during each forward pass.

---

## 2. Memory: MoE is more expensive

MoE saves compute but often **increases memory requirements**.

Even if most experts are inactive for a given token, the model still needs to store the weights of all experts.

So:

- Dense 7B model: store ~7B parameters.
- MoE 48B model with 8B active parameters: still store ~48B parameters.

For inference, this means MoE models often require more memory, more GPUs, or more aggressive sharding.

The efficiency trade-off is:

> MoE lowers FLOPs but increases weight memory.

For large MoE models, expert parallelism is commonly used, where different experts are placed on different accelerators. This can make the model runnable, but it introduces communication overhead and complicates deployment.

---

## 3. Training efficiency: larger capacity at lower compute

MoE models can scale total parameter count while keeping per-token compute relatively low. This allows training larger-capacity models at a given compute budget.

However, training MoE models is more complex:

- The optimizer state scales with **total parameter count**, not just active parameters.
- Routing decisions introduce irregular memory access.
- Load balancing is needed so experts are used roughly equally.
- Routing losses, capacity factors, and expert assignment add implementation complexity.
- Training can be less stable if one expert is overused or ignored.

A dense model has more regular, predictable training behavior. A MoE model has extra degrees of freedom that can help capacity scaling but add engineering and optimization burden.

---

## 4. Inference latency: MoE can be faster or slower depending on hardware

MoE can reduce compute, but it does not automatically reduce latency.

Potential benefits:

- Fewer active FLOPs per token.
- Better throughput on large batch sizes.
- Better quality at a given compute budget.

Potential drawbacks:

- Need to load many expert weights into memory.
- Need to communicate between accelerators if experts are sharded.
- Routing and dispatching tokens to experts adds overhead.
- Low utilization if expert load is imbalanced.
- Small batch sizes may not use experts efficiently.

For a well-optimized MoE model on a large multi-GPU system, latency can be competitive or better than a dense model with equivalent quality. But on a single GPU or with small batches, the memory and communication overhead can hurt.

---

## 5. Load balancing and token distribution

MoE models require a routing mechanism to decide which experts process each token.

If routing is poorly balanced, problems arise:

- Some experts get overloaded.
- Some experts get underused.
- Capacity limits may drop or delay tokens.
- Certain GPUs may sit idle while others are busy.

Common remedies include:

- Auxiliary load-balancing losses.
- Expert capacity factors.
- Top-k routing.
- Noisy or stochastic routing.
- Expert parallelism with load-aware scheduling.

Dense transformers do not have this problem: every token uses the same layers, so utilization is highly predictable.

---

## 6. Communication overhead

In distributed systems, MoE models often require token routing across accelerators.

Typical MoE serving patterns:

1. Tokens are dispatched to the required experts.
2. Expert computation happens on the appropriate device.
3. Results are combined and returned.

This requires communication, often all-to-all or all-gather style patterns.

Dense models have simpler communication patterns, such as tensor or pipeline parallelism, without token-level routing.

So the trade-off is:

> MoE can reduce compute but increases communication and scheduling complexity.

This is especially important for low-latency inference or single-node deployments.

---

## 7. Quality scaling

MoE models tend to offer a better quality-to-compute ratio.

At the same per-token FLOPs, an MoE model can often outperform a dense model because its total parameter capacity is larger.

The extra inactive parameters act like a larger “knowledge store,” even though only part of it is used per token.

This is one reason MoE architectures are attractive for frontier-scale models: they can increase model quality without proportionally increasing inference FLOPs.

But this advantage is less obvious when the total parameter count is too large to store efficiently.

---

## 8. Simpler deployment favors dense models

Dense transformers are simpler:

- Standard dense GEMM kernels.
- Regular memory access.
- Easier quantization.
- Easier kernel optimization.
- No routing.
- No expert scheduling.
- No load-balancing tuning.

For small or medium models, or for environments with limited hardware, a dense model is often easier and more efficient in practice.

MoE becomes more attractive when:

- The model is very large.
- Multiple accelerators are available.
- Batch sizes are large enough to amortize routing overhead.
- Expert parallelism is supported.
- Quality-per-FLOP is more important than raw memory simplicity.

---

# Summary table

| Dimension | Dense transformer | Mixture-of-Experts |
|---|---|---|
| Parameters per token | All parameters | Subset of experts |
| Compute per token | Scales with total params | Scales with active experts |
| Memory requirement | Proportional to total params | Proportional to total params, usually larger |
| Training complexity | Lower | Higher |
| Load balancing | Not needed | Needed |
| Hardware utilization | Highly predictable | Potentially uneven |
| Communication overhead | Lower | Higher, especially with expert parallelism |
| Quality scaling | Good but proportional compute cost | Better quality at lower per-token FLOPs |
| Deployment simplicity | Simpler | More complex |
| Best use case | Small/medium models, simple serving | Large models, multi-GPU, compute-efficient inference |

---

# Bottom line

The central efficiency trade-off is:

> **MoE increases total parameter capacity while reducing active compute per token, but it increases memory, communication, routing, and training complexity.**

A dense transformer is simpler, more predictable, and easier to serve. An MoE model can be more compute-efficient and can achieve stronger scaling behavior, but only if the hardware and serving stack can absorb the memory and expert-routing overhead.
