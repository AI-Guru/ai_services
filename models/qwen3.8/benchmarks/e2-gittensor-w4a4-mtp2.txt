Dense transformers and mixture-of-experts (MoE) transformers differ mainly in how they handle feed-forward computation. A dense transformer applies the same FFN block to every token at every layer. An MoE model replaces each FFN with many “expert” FFNs and a router that sends each token to only a small subset of experts, usually the top-1 or top-2.

## Core architectural difference

### Dense transformer
For each token, every layer’s FFN is fully used.

- **Parameters used:** all FFN parameters.
- **FLOPs per token:** proportional to total model size.
- **Behavior:** deterministic, uniform compute for all tokens.
- **Scaling:** increasing model capacity increases both memory and compute roughly together.

### Mixture-of-experts transformer
For each token, a router selects a few experts, and only those experts process the token.

- **Parameters used:** only the selected experts for that token.
- **FLOPs per token:** much lower than total parameter count.
- **Behavior:** compute is conditional: easier tokens may use fewer experts; harder tokens can use more.
- **Scaling:** total capacity can grow without growing per-token compute proportionally.

## Efficiency trade-offs

| Dimension | Dense Transformer | Mixture-of-Experts Transformer |
|---|---|---|
| Total parameters | Small/moderate | Usually larger |
| Active parameters per token | All parameters | Only a subset |
| Compute per token | Higher | Lower |
| Memory footprint | Lower | Higher |
| Inference simplicity | Simpler | More complex |
| Training stability | Easier | Harder due to routing/load balancing |
| Parallelism | More standard | Often needs expert parallelism |
| Scaling behavior | Compute grows with size | Capacity can grow faster than compute |

## Main efficiency trade-offs

### 1. Compute vs. capacity
The main benefit of MoE is that you can store more total parameters, giving the model more capacity, while spending less compute per token.

For example, a model may have 128 experts but activate only 2 per token. The total parameter count can be much larger than a dense model, but each token only processes a small fraction of the experts.

This is useful when you want:

- a larger model without proportionally higher FLOPs,
- better quality at a fixed compute budget,
- more model capacity for long-tail or diverse tasks.

The trade-off is that total model size grows even though per-token compute does not grow as much.

### 2. Memory and storage cost
MoE models usually require storing many more parameters than an equivalent dense model.

This creates trade-offs:

- larger checkpoints,
- larger inference memory footprint,
- harder deployment on limited hardware,
- potential need to shard, offload, or quantize experts,
- higher cost to keep all experts in memory.

A MoE model can be computationally efficient but memory-heavy.

### 3. Inference efficiency
During inference, especially at small batch sizes, models are often memory-bandwidth-bound rather than compute-bound.

MoE helps if:

- the model fits in memory,
- the active expert compute is much lower than the dense baseline,
- batching allows experts to be reused across tokens.

But it may not be as fast as a similarly sized dense model if:

- the attention, embedding, and output layers remain dense,
- all experts must be stored in memory,
- routing overhead is non-negligible,
- expert load becomes unbalanced,
- the model is too large for the available accelerator.

So MoE can improve throughput and reduce FLOPs, but it does not automatically reduce latency.

### 4. Training efficiency
MoE can reduce FLOPs per token during training, which can be attractive for large-scale training.

However, training is more complicated:

- the router must learn good token-to-expert assignments,
- experts must be used roughly evenly,
- load-balancing losses or capacity constraints are often required,
- some experts may become underused while others become bottlenecks,
- expert parallelism can introduce communication overhead,
- debugging and monitoring routing behavior is harder.

Dense transformers are simpler and more predictable: every token uses the same FFNs, and there is no expert imbalance problem.

### 5. Communication and parallelism
MoE models often use expert parallelism, where different experts are placed on different devices.

This can improve scaling, but it introduces overhead:

- tokens must be routed between devices,
- communication cost increases with expert count and batch size,
- load imbalance can waste compute on some devices,
- fault tolerance becomes harder because a failed expert can affect many tokens.

Dense models scale more straightforwardly with standard tensor or pipeline parallelism.

### 6. Quality and scaling behavior
MoE can provide a better scaling story: you can increase model capacity without increasing compute per token as much.

In practice, this can yield:

- better accuracy for a given FLOP budget,
- stronger performance on heterogeneous workloads,
- more flexibility in conditional computation.

But the gains are not free:

- larger memory requirements,
- more complex training,
- routing overhead,
- possible degradation if experts are poorly balanced,
- diminishing returns as the number of experts grows.

## Bottom line

Dense transformers use all parameters for every token. MoE transformers use a larger parameter pool but activate only a small subset per token.

The key trade-off is:

> **MoE trades larger memory footprint and more complex routing/training for lower per-token compute and higher capacity.**

Dense models are simpler, easier to train, and easier to deploy. MoE models can be more compute-efficient and can scale capacity more aggressively, but they introduce overhead in memory, communication, load balancing, and operational complexity.
