How much concurrency does one 96 GB Blackwell card actually take before it stops giving anything back? There is no single number. The ceiling moves with prompt length, and it moves fast: peak throughput varies 7.1x across prompts from 512 to 10,000 tokens on identical hardware, weights and flags — and the concurrency you can serve at interactive latency halves every time the prompt doubles.

The answer

Two ceilings, and they are not the same ceiling

"Running out of air" means two different things, and the gap between them is where most capacity planning goes wrong. The card stops feeling fast long before it stops getting faster.

The interactive limit is the highest concurrency that still answers in under 5 seconds at the median. The throughput ceiling is where aggregate tok/s reaches 90 % of its measured peak — past that, more concurrency buys queue, not work. Both are read directly off the measurements below.

The pattern

Between 2K and 8K the interactive budget halves on every doubling of the prompt: 16 → 8 → 4. Prefill is quadratic in nothing here — it is simply linear work that concurrency multiplies, and the decode time it steals is time no stream gets back.

Long context

At 100K the question stops making sense

Asked whether the card would hold 15-20 parallel streams at 100-150K context, the honest answer is that it will hold them and they will not help.

The KV pool is 1,605,632 tokens, so sixteen 100K streams (1.6M) physically fit, and ten 150K streams (1.5M) fit comfortably. Memory is not the constraint. Prefill throughput is, and it saturates at concurrency one.

Capacity, stated honestly

For long context, one RTX PRO 6000 is a rate, not a concurrency: about 4 completed requests per minute at 100K and 2 per minute at 150K. Running twelve in parallel instead of one does not raise that — it lowers it, from 3.97 to 3.17 req/min, while the median wait goes from 18 seconds to over four minutes.

Read the "output tok/s" column with care: at 100K prompts the 300 generated tokens are 0.3 % of the work, which is why it reads 16-21 while the card is genuinely moving 6,000+ tokens a second.

Corrections

Three ways this measurement lied first

All three produced numbers that looked entirely plausible. All three were the harness, not the engine — which is exactly why they are worth writing down.

Trap 01 — reported as an engine failure

A 60-second client timeout books slow requests as errors

GuideLLM aborts a request after its backend timeout — 60 s by default — and records it as an ERROR, not as slow. The first 100K run returned 33 errored / 4 ok at concurrency 16, with a latency curve that looked like the server falling over.

The server was fine. Every request simply took longer than the harness permitted. The long-context levels were re-run at a 1800 s timeout and came back with zero errors.

Trap 02 — a 52 % collapse that was not there

A 60-second window is not a measurement at high concurrency

With 64 concurrent 10K-token prompts, vLLM logs Running: 6 reqs, Waiting: 58. The window closes while the engine is still draining the prefill backlog, and because only completed requests are averaged, the level reads far too low.

The same cell measured 166.9 tok/s at 60 s and 324.2 tok/s at 300 s. The dramatic collapse of the longest curve at concurrency 64 was entirely this artifact. There is no collapse — there is a plateau. The 8K and 10K cells at concurrency 32-64 above are the 300 s numbers.

Trap 03 — zero requests sent

A fixed prompt length is rejected outright

Asking for an exact prompt size means prompt_tokens_stdev=0, which GuideLLM's pydantic config refuses (Input should be greater than 0). The run dies during data deserialization, before a single request reaches the server, and the failure reads like a connection problem.

Fixed lengths have to be expressed as a tight band instead: stdev=1 with min/max at ±1 %.

Method

How to reproduce it, and what it does not cover

One boot, one checkpoint, one harness. Output length is pinned at 300 tokens (132-500) across every scenario so that prompt length is the only variable. Prefix caching is on — vLLM's default — but the hit rate was 0.0 % throughout, because GuideLLM's synthetic prompts are unique. The prompt-length axis measures real prefill, not cache hits.

./scaling.sh nvfp4-w4a4 gittensor-model-hub/Qwen3.8-27B-NVFP4-RTX5090   # prompt-length grid
./lc_rerun.sh        # 100K / 150K, GLLM_TIMEOUT=1800
./recheck_run.sh     # 300 s steady-state cells for 8K/10K at conc 32-64
python3 scaling_table.py > benchmarks/SCALING-GRID.md

Two limits on these numbers

FP8 is not measured here. This grid is 4-bit only. The single-stream FP8 datapoint — 45.6 tok/s, 2.45x slower than W4A4 — remains the only fp8 figure, so no fp4-versus-fp8 scaling comparison exists yet. The harness takes a checkpoint id as its argument and the FP8 checkpoint ships MTP weights, so the identical grid can be run against it unchanged.

Do not splice these rows against the 2026-08-18 concurrency table. Same image, same flags, same checkpoint — but this grid's 2K row reads 129.5 tok/s at concurrency 1 where the earlier chat row reads 111.3, on a slightly narrower prompt distribution. MTP acceptance is prompt-sensitive and that gap is larger than the ~3 % cross-boot spread on this card. Each table is internally consistent; across tables, compare shapes rather than absolute numbers.
