The saturation point is set by the output:input ratio, not by request count. Rank the five workloads by how much decode work they do per token of prefill and you get exactly the observed ordering. Prefill competes with decode for the same SMs, so a prefill-dominated workload spends added concurrency on context it has already paid for rather than on tokens you asked for.

Aggregate throughput

rag, agentic and summarization all turn downward past their peak — past saturation the extra concurrency is not merely wasted, it is negative. chat and codegen have not turned over at 64, so their true ceiling is above this ladder.

Per-request decode rate

All five scenarios start at 104.9–107.9 tok/s at concurrency 1 — an independent reproduction of the 107.3 tok/s single-stream figure from test_chat.py, on a different harness with different prompts. From there each request's share decays roughly as 1/concurrency, fastest for the prefill-heavy workloads: at concurrency 64 a summarization request sees 7.8 tok/s while a codegen request still sees 20.9.

Tail latency — the real constraint

Throughput ceilings are generous; tail latency is not. chat sustains a 253 ms TTFT p95 at concurrency 16 but 4,753 ms at 64. summarization goes from 1,342 ms at 8 to 44,010 ms at 64. In every scenario the p95 wall arrives well before the throughput ceiling — so if you are sizing for interactive use, pick the concurrency from this chart, not from the throughput one.

Prefill throughput

Prefill keeps climbing even where decode throughput has turned over — rag reaches 14,204 tok/s of prefill at concurrency 64 while its output throughput is falling. That is the mechanism behind the saturation: the GPU is busy, just not on the tokens you are measuring.

One anomaly, flagged not explained. codegen's prefill at concurrency 64 reads 16,263 tok/s — a 7× jump from 2,216 at concurrency 32, out of line with every other series in the sweep. Treat it as a probable measurement artifact rather than a result; it is the one number here I would not build on without re-running.

Two things that did not happen

Over-subscribing KV produces queueing, not preemption. agentic and summarization at concurrency 64 need 1,075k and 787k tokens against a 577,749-token pool. grep -c preempt on the vLLM log returns 0 — the scheduler simply refuses to admit more requests than fit and queues the rest. That is why agentic TTFT p50 jumps from 1,895 ms at concurrency 16 to 14,346 ms at 32: requests are waiting for admission, not being evicted mid-flight. The cost of over-subscription shows up entirely as queueing delay.
The 23 "errored" requests at agentic/64 are a harness artifact, not a server failure. vLLM logged zero errors across the entire sweep. GuideLLM's scheduler_state shows duration_exceeded: true on its 90-second window, and median request latency at that rung was 72 s — so anything dispatched after ~18 s could not finish in time and was recorded as errored. Every other rung in every scenario had 0 errors.

Why the server config was changed first

This sweep was run at --gpu-memory-utilization 0.94 / --max-num-seqs 64, not the 0.90 / 32 used for the single-stream benchmark. Both changes were load-bearing:

SettingSingle-stream runThis sweepEffect
--gpu-memory-utilization0.900.94KV pool 448,413 → 577,749 tokens
--max-num-seqs3264ladder can exceed its own top rung
--max-num-batched-tokens81928192unchanged — see below
VRAM in use88.7 GB92.7 GBof 97.9 GB total

Since vLLM 0.21 the utilization figure includes CUDA graph memory profiling, so 0.90 behaves like 0.8529 did previously — vLLM's own startup log recommends 0.9471 to recover the old effective KV size. More concretely: agentic at concurrency 32 needs 537k tokens in flight, which does not fit in the old 448k pool but does fit in the new 577k one. At 0.90 that rung would have measured KV starvation rather than concurrency scaling.

--max-num-batched-tokens was deliberately left at 8192. Raising it would speed up prefill-heavy scenarios somewhat, but the profiler reserves activation memory at that size, and that memory is worth more as KV — starvation causes queueing that costs far more than larger prefill chunks save. Chunked prefill handles 16k prompts fine at 8192.

Methodology

  • Harness: guidellm 0.5.4, --profile concurrent with a pinned rate ladder — the same regime as models/qwen3.6/bench-guidellm-concurrent.sh. The sweep profile dispatches 512 concurrent requests and, on long scenarios, completes nothing inside the per-rate window.
  • Ladder 1,4,8,16,32,64; 90 s per rung; 15% warmup; synthetic prompts at the stated mean ± stdev token counts.
  • Base model only — no speculative decoding. DFlash is measured separately.
  • Tokenizer/processor: poolside/Laguna-S-2.1-NVFP4.
  • Sole tenant on the card for the whole run; nothing else resident.
  • "Per-req tok/s" is derived as 1000 / inter_token_latency_ms (median), not measured directly.
  • "KV needed" is concurrency × (mean prompt + mean output) — an estimate of tokens in flight, compared against the 577,749-token pool.

Not measured: prefix-cache hit behaviour (guidellm's synthetic prompts share little prefix, so --enable-prefix-caching contributes ~nothing here and real traffic would do better), long-context behaviour beyond 16k prompts, and quality under load.
