Headline

123 tok/s
warm single-stream decode with DFlash (k=6) — +15% over the 107.3 tok/s no-speculation baseline

A 117.6B-parameter model fits and serves comfortably on one card because only 8.5B parameters activate per token. The NVFP4 weights take ~72 GB, leaving room for a 448,413-token KV cache at --gpu-memory-utilization 0.90 — 1.71× the model's full 262,144-token context.

The one tuning result that matters: the model card's num_speculative_tokens: 15 produces no speedup at all on this card (108.6 tok/s, statistically identical to the 107.3 baseline). Dropping to k=4–8 is what delivers the ~15% gain. See the sweep below.

Why k=15 fails: per-position acceptance

vLLM reports acceptance per draft position. The drafter is strong on the first token and decays fast — beyond position ~5 it is essentially guessing, but the target model still pays to verify every drafted slot. Long drafts buy near-zero extra accepted tokens at full verification cost.

Mean acceptance length barely moves from k=6 (2.55) to k=15 (2.57) — going from 6 to 15 drafted tokens buys 0.02 extra accepted tokens per step. poolside report 2.9–3.1 on the DGX Spark; we measure 2.28–2.62 on this prompt mix, in the same neighbourhood but below their figure.

Time to first token

Speculation is not free at the front of a request: the drafter has to run before the first token can be verified. Warm TTFT roughly doubles, from 32 ms to 50–60 ms. That is still fast enough to be invisible in chat, but it is a real regression if you are optimising for latency on very short completions.

Cold-run TTFT is much worse and depends on draft depth: the first request after startup measured 73 ms at baseline, ~690 ms at k=4/k=6, and ~3050 ms at k=8/k=15. Always --warmup before trusting a TTFT number here.

Does DFlash cost quality?

In principle, no. vLLM's RejectionSampler docstring states it "strictly follows the algorithm described in arxiv.org/abs/2211.17192" — Leviathan et al., the provably distribution-preserving speculative decoding algorithm. Rejected draft tokens are resampled from the target model's corrected distribution, so acceptance rate is a speed dial, not a quality dial. Our 25.9% acceptance means the drafter wastes compute, not that the output is worse.

Not verified here. No quality measurement was run. Two reasons not to simply assume it: outputs will not be bit-identical to baseline (speculation changes batch shapes and kernel paths, so logits differ in the last decimals), and this repo has previously seen INT4+DFlash destabilise tool-calling on Qwen3.6-27B where FP8+DFlash was fine. Laguna is structurally protected against that specific trap because poolside ship a quantization-matched drafter (Laguna-S-2.1-DFlash-NVFP4), which is what was used — but "avoids the known failure mode" is not the same as "verified".

Three fixes needed to boot

Serving this checkpoint on vllm/vllm-openai:nightly required three environment fixes, all now baked into the compose files. Each presented as a generic crash-loop far from its cause.

  1. flashinfer version skew. Installing flashinfer-python/-cubin from PyPI stable while taking -jit-cache from the cu130 nightly index gives 0.6.15 against a 0.6.16 cubin, and the NVFP4 MoE dies at load: TypeError: Mismatched number of arguments when calling init(...). Expected 9 but got 8. Fix: pin all three to the same nightly version.
  2. quack-kernels vs cutlass-dsl. The base image's quack-kernels 0.4.1 is incompatible with the nvidia-cutlass-dsl 4.6.0 the vLLM upgrade pulls in: AttributeError: module 'cutlass.cute.core' has no attribute 'ThrMma' during the MoE router warmup. That warmup is gated only on compute capability ≥ 9.0, so no serve flag skips it. Fix: pip install -U quack-kernels.
  3. --moe-backend triton does not apply to NVFP4. The vLLM recipe lists it for DFlash, but it targets the BF16/INT4 checkpoints. On NVFP4 vLLM rejects it outright: ValueError: moe_backend='triton' is not supported for NvFP4 MoE. Leave it on auto, which selects FLASHINFER_CUTLASS.
Reasoning parser caveat. poolside_v1 only splits reasoning out when the request sends chat_template_kwargs; otherwise it falls back to an identity parser and </think> leaks into content. Worse, when thinking is enabled the reasoning text is stripped from content but reasoning_content is never populated in the non-streaming response — those tokens are billed and discarded. Send chat_template_kwargs: {"enable_thinking": false} for clean direct answers. Note the template variable is enable_thinking, not thinking, and it defaults to true.

Methodology

  • Harness: models/shared/test_chat.py, the repo standard.
  • Command: 
    python3 test_chat.py --base-url http://localhost:11440/v1 \
  --model laguna-s-2.1 --runs 5 --warmup --no-think
  • Single stream, batch size 1. Default prompt (MoE vs dense transformers explainer), 245–628 tokens generated per run.
  • Baseline and k=6 measured over 5 runs; k=4, k=8 and k=15 over 3 runs each. Warm figures drop run 1.
  • Served at --gpu-memory-utilization 0.90 / --max-num-seqs 32. The compose now defaults to 0.94 / 64 for serving; neither knob affects batch-1 decode rate.
  • Only one model resident on the card at a time; the usual Qwen3.6-27B tenant was stopped for the duration.
  • Acceptance figures come from vLLM's own SpecDecoding metrics log lines, not derived from throughput.
Known limitation: --no-think is a no-op on this family. It sends a top-level enable_thinking, which vLLM 0.26 ignores — only chat_template_kwargs.enable_thinking works. So every number here was measured with thinking on. That does not distort tok/s (decode rate is the same either way), but it means these are not "answer-only" latencies.

Concurrency and long-context prefill behaviour are measured separately in the GuideLLM concurrency sweep. Quality was not measured: poolside report 70.2% Terminal-Bench 2.1, 78.5% SWE-bench Multilingual and 59.4% SWE-Bench Pro for this model, none independently verified here.

Reproduce

# baseline, no speculation
cd models/laguna-s
docker compose --env-file ../../.env -f docker-compose.vllm-118b-nvfp4-rtx.yml up -d

# DFlash — sweep the draft depth with SPEC_TOKENS (default 4)
SPEC_TOKENS=6 docker compose --env-file ../../.env \
  -f docker-compose.vllm-118b-nvfp4-dflash-rtx.yml up -d

# benchmark
cd ../shared
python3 test_chat.py --base-url http://localhost:11440/v1 \
  --model laguna-s-2.1 --runs 5 --warmup --no-think

# acceptance metrics
docker logs laguna-s-118b-nvfp4-dflash 2>&1 | grep "SpecDecoding metrics" | tail -1
