Only chat parallelizes. Every workload with a prompt above ~4K or an output above ~800 tokens saturates at roughly single-user throughput. 256K beats 1M on all five scenarios — the 1M config's KV pool is 4.7× larger but its prefill batch budget is half (8192 vs 16384), so it cannot feed the requests it could hold.

Findings

  • The ceiling is not purely prefill. Codegen has only a 4K prompt yet shows zero scaling (95.0 → 99.6 tok/s) — its 1500-token output is what caps it. Long outputs do not batch either.
  • 1M RAG scales at 0.9× — concurrent load makes it slower than serving one request at a time. An 8K prompt consumes essentially the whole 8192-token prefill step, so requests serialize and pay scheduling overhead on top.
  • Context length is nearly free at low load. Single-user throughput differs by <5% between 256K and 1M. The cost of 1M appears only under concurrency.
  • 1M is slightly more responsive under load — ITL 56.6 ms vs 67.5 ms at the top chat rate. It serves fewer requests, so each gets more attention. A real trade, not purely a loss.
  • No speculative decoding. DSpark is unavailable on SM120 in stock vLLM, so every number here is a floor; vllm PR #41834 would add an estimated 40–50%.

Recommendation: serve 256K. It wins every measured workload, and nothing in this set uses prompts beyond 256K. Reserve 1M for single-user long-context work.

Method & caveats

GuideLLM 0.5.4 --profile sweep, 10 rate points per scenario, 120 s each, 10% warmup, run via bench-guidellm-parallel.sh. Both configs on identical hardware, sequential container swap, no other GPU load. Prefix caching enabled in both (matches deployment) — these are not cache-cold numbers. The 1M RAG synchronous point read 63.4 tok/s in the sweep; a 60 s re-run gave 72.9 tok/s, so the single-user figure carries real variance — the saturated collapse is the robust finding. Raw data: benchmarks/guidellm/{256k,1m}/<scenario>/benchmark.json.
